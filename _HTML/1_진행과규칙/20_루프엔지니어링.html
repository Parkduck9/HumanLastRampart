1. 루프 엔지니어링이란 (조사 요약)

  • 2026년에 생긴 말. AI에게 매번 사람이 지시를 쳐 주는 대신, AI가 스스로 "계획 → 실행 → 결과 확인 → 고치기"를 되풀이하다 목표에 닿으면 멈추는 고리(루프)를 설계하는 일이다.
  • 이름은 애디 오스마니(구글 개발자)의 글(2026년 6월)에서 퍼졌고, 클로드 코드 팀도 "지시를 쓰는 대신 고리를 쓴다"고 말한다.
  • 여러 글이 공통으로 꼽는 고리의 부품 다섯 가지:
  • 실행자 — 코드를 짜는 AI
  • 검증자 — 결과를 판정하는 것. 가장 중요하다. "검증 없는 고리는 그냥 자동화일 뿐"
  • 되먹임 길 — 실패 이유를 다음 시도에 짧게 넘김
  • 성공 출구 — 무엇을 보면 "끝"인지 미리 정함
  • 상한 — 시도 횟수 상한, 비용(토큰·크레딧) 상한
  • 검증은 두 층이 좋다: 기계 판정(시험·컴파일, 말로 속일 수 없음) 이 마지막 관문이고, AI의 평가(사진 보고 판단 등)는 그 앞의 보조.
  • 흐름(언제 멈추고 다시 할지)은 AI의 기분이 아니라 미리 정한 규칙·스크립트가 정한다.
  • 비용 경고: 여러 에이전트를 함께 돌리면 토큰을 크게 더 쓴다(한 글에 따르면 약 15배, 원문 확인은 못 함) — 사용자가 정한 "토큰 급감 시 다중 실행 점검" 규칙과 같은 이야기.

2. 받아 온 보고서 검증 (제미나이 작성, 25항목)

보고서는 무협 게임용이라 그 세계관 항목(충·효·의, 대사 말투, 초식 콤보, 코아 조언자 등)은 우리와 상관없다. 또 "준비도 92%" 같은 막대 수치와 25항목 자체 채점은 근거가 없는 숫자라 버린다. 남길 것과 고칠 것:

보고서 항목판정우리 프로젝트에서는
01 실행자와 검증자 분리채택이미 있음: 유니티 일괄 시험 + 사진 시험. 화면 모양 판정은 사진으로, 마지막은 사용자
02 실행자가 시험 기준을 몰래 낮추는 위험고쳐서 채택우리는 시험도 함께 고친다(오늘도 전체 흐름 시험을 자유 배치에 맞게 고침). 그래서 "금지" 대신: 시험 파일을 고치면 이유를 기록하고, 판정을 느슨하게 하는(기대값 낮춤·검사 삭제) 수정은 사용자에게 따로 알린다
03 무작위로 결과가 흔들림 → 고정 씨앗·천 번 반복이미 됨전투는 고정 씨앗(DeterministicRandom)으로 같은 결과. 천 번 반복은 불필요 — 측정 시험(Fuzz10·Funnel40Sweep)으로 충분
04 작업 트리 여러 개 → 유니티 캐시 용량 폭발채택(이미 일부)코덱스 카드 작업 트리는 그림만 다룬다(유니티를 열지 않음). 코드 검증은 본 작업 폴더 한 곳에서만
05 화면 없이 도는 명령줄 시험이미 됨 + 고칠 점밤 시험 스크립트가 있다. 단 오늘 유니티 허브 프로세스를 편집기로 잘못 보고 멈춤 → 편집기 경로만 보게 고친다
06 상태 파일 동시 쓰기 충돌이미 됨소유 폴더 분리(live/claude, live/codex), 기록은 맨 아래 추가만
14 최대 반복 상한채택(값 변경)한 항목에 3번까지 고쳐 보고, 넘으면 멈추고 보고
15 실패 로그 통째로 넘기지 않기채택실패 시 "원인 3줄 + 실패 시험 이름 + 로그 핵심 20줄"만
16 저장 파일 하위 호환채택(중요)저장 구조를 바꿀 때마다 옛 저장 불러오기 시험. 오늘 지형 손질에 칸이 아닌 자리값을 더했으므로 해당
17 작은 단위로 쪼개기채택고리 한 바퀴 = 설계 문서 항목 하나
18 같은 실패 2번이면 방법 바꾸기채택
19 개악 시 자동 되돌리기(자동 리셋)고쳐서 채택자동 리셋은 남의 파일까지 지울 위험 → 내 파일만, 파일 단위로 마지막 통과 상태로 되돌린다
21 성능 관문채택(우리 값)그리기·전투를 건드리면 프레임 측정 시험(FrameCost)을 돌려 이전과 비교
23 막히면 사람에게 묻기채택(이미 규칙)FirstRead "모르면 묻는다"와 같음
24 글자 넘침채택(나중)한글 화면 글이 판 밖으로 넘치는지 — 사진 시험에서 확인
07~13·20·22 무협 서사·밸런스·코아버림우리 게임과 무관
막대 그래프 %·자체 채점버림근거 없는 숫자

3. 우리 작업 고리 (제안)

[항목 고르기] → [끝 조건 미리 적기] → [만들기] → [관문 1~4] → 통과 → [마무리]
                                         ↑            │ 실패
                                         └── 되먹임 ──┘ (3번까지, 같은 실패 2번이면 방법 바꿈)

3.1 한 바퀴의 단계

  1. 항목 고르기 — 사용자가 승인한 설계 문서의 항목 하나. 결정이 남아 있으면 시작하지 않고 묻는다.
  2. 끝 조건을 먼저 적는다 (고리 기록에) — 예: "전체 흐름 시험에서 토벽 2개 짓기 성공 + 지도 사진에 막을 칸이 초록으로 보임".
  3. 만들기 — 내 소유 파일만.
  4. 관문
  5. 관문 1 컴파일·편집 시험 (-testFilter "!SimProbe")
  6. 관문 2 화면 시험 (PlayMode, 사진 저장)
  7. 관문 3 성능 (그리기·전투를 건드렸을 때만 FrameCost)
  8. 관문 4 사진 판정 — 끝 조건에 적은 장면을 사진으로 보고 확인
  9. 관문 5 사용자 — 보기 좋은지·느낌 같은 주관 항목은 사진을 보내고 물음 (고리는 여기서 멈춤)
  10. 실패하면 — 원인 3줄·실패 시험 이름·로그 핵심만 기록하고 다시. 같은 실패 2번이면 다른 방법. 3번 실패면 멈추고 보고.
  11. 마무리 — 내 파일만 파일 단위 커밋, ROADMAP 문서·화면 갱신, 고리 기록에 결과 한 줄.

3.2 고리 기록 (외부 기억)

  • 파일: Docs/collab/live/claude/loop_log.md (Claude만 씀, 맨 아래에 추가만)
  • 한 바퀴마다 다섯 줄: 항목 · 끝 조건 · 시도 번호 · 결과(통과/실패 이유 3줄) · 다음 할 일
  • 토큰이 바닥나 코덱스가 이어받을 때도 이 파일 마지막 줄부터 읽으면 된다.

3.3 상한과 비용

  • 한 항목 시도 3번, 한 세션 동시 실행 에이전트 최대 3개(조사용만), 코덱스 카드는 크레딧 확인 뒤.
  • 토큰이 적게 남으면(자동 압축 근처) 새 항목을 시작하지 않고 고리 기록과 넘겨받기 문서를 먼저 쓴다.

3.4 클로드 코드 기능과의 연결 (선택)

  • /loop: 정해진 간격이나 스스로 정한 간격으로 같은 지시를 되풀이 — 밤 시험 결과 확인, 코덱스 카드 끝남 확인 같은 기다림에 쓸 수 있다.
  • 일반 작업은 위 3.1 단계를 대화 안에서 그대로 따르면 된다. 자동 반복을 켜는 것은 사용자가 원할 때만.

4. 바로 고칠 것 (승인 시)

  1. 밤 시험 스크립트: 유니티 허브(unity.exe serve)를 편집기로 착각하지 않게 — 편집기 경로만 검사.
  2. loop_log.md 만들기, MAINTENANCE에 "작업 고리" 한 장 추가.
  3. 옛 저장 불러오기 시험 1개(지형 손질 자유 배치 이전 저장).

5. 사용자 확인 질문

  1. 한 항목 시도 상한 3번으로 할까요? (보고서는 5번)
  2. 시험을 느슨하게 고칠 때 매번 알림으로 할까요, 아니면 아예 금지할까요?
  3. /loop 자동 반복은 기다림(밤 시험·코덱스 카드 확인)에만 쓸까요?
