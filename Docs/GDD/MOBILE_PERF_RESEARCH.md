# 모바일(아이폰 14 Pro) 60Hz 가능성 조사

- 상태: **조사 메모 — 결정 아님.** 현재 플랫폼은 PC(D-002)다. 모바일 지원은 사용자 결정이 필요하다.
- 작성: Claude / 2026-10-13 / 사용자 요청 "아이폰 14 Pro 정도에서 60Hz로 돌릴 수 있게 최적화할 방법(DOD 외에도)"
- 근거: PerfLab 측정 M1·M2(PERF_PROTOTYPE.md 8장), D-020·D-021·D-024. 기기 수치는 공개 사양 기준이며 **실측하지 않았다.** 성능 배수는 모두 추정이다.

## 1. 출발점: 지금 구조가 데스크톱에서 쓰는 시간

## 2. 아이폰 14 Pro는 어느 정도인가 (공개 사양, 추정 포함)

| 항목 | 아이폰 14 Pro | 의미 |
|---|---|---|
| CPU | A16: 고성능 코어 2개 + 효율 코어 4개 | Job을 나눠 돌릴 코어가 데스크톱(32스레드)보다 훨씬 적다. **병렬 계산 처리량은 대략 1/6~1/10로 추정** |
| GPU | Apple 5코어, 타일 기반(TBDR) | 데스크톱과 그리는 방식이 달라 **잘라내기(clip/discard) 셰이더가 특히 비싸다** (3장) |
| 메모리 | 6GB (앱이 쓸 수 있는 양은 그보다 훨씬 적음) | 지금 데이터는 수십 MB 수준이라 문제 아님 |
| 화면 | 2556×1179, 최대 120Hz | 60Hz면 프레임당 16.7ms |
| **발열** | 오래 고부하면 성능을 낮춤(스로틀링) | **짧게 60이 나와도 10~20분 유지가 진짜 기준.** 가장 큰 위험 |

- 단순 환산: 데스크톱 CPU 약 2ms × 6~10배 ≈ **12~20ms**. 60Hz 예산(16.7ms)에 걸치거나 넘는다. 발열을 생각하면 **지금 규모 그대로 60Hz 유지는 어렵다**고 본다.
- 그래서 "DOD를 더 빠르게" 하는 것만으로는 부족하고, **계산할 양 자체를 줄이는 방법**이 필요하다(4장).

## 3. 모바일 GPU에서 지금 구조를 바꿔야 하는 점

| 지금 (PC 기준) | 모바일 문제 | 바꿀 방법 |
|---|---|---|
| 사각형 + 알파 잘라내기(clip) | Apple GPU는 숨은 면을 미리 걸러 그리기를 줄이는데(HSR), **잘라내기가 있으면 이 최적화가 꺼진다.** 겹친 군중에서 비용 급증 | ① 사각형 대신 **그림 모양에 딱 맞춘 다각형 메시**로 투명 부분을 줄이고 잘라내기 없이 그린다 ② 또는 멀리 있는 적은 잘라내기 없는 작은 점·단색 실루엣으로 |
| 개체당 32바이트 그리기 데이터 | 매 프레임 6만 × 32B ≈ 2MB 전송 | **16바이트로 압축**(위치 반정밀도·프레임 번호를 정수 하나에) → 절반 |
| 내부 해상도 = 화면 절반 | 2556×1179의 절반도 모바일엔 큼 | 내부 해상도 **1/3**(약 852×393) + 정수 3배 확대. 도트 게임이라 화질 손실이 작다. **동적 해상도**(발열 시 자동으로 낮춤) |
| URP 기본 설정 | 후처리·그림자·HDR은 모바일에서 비쌈 | 템플릿에 이미 있는 `Mobile_RPAsset` 사용, 후처리·실시간 그림자·HDR 끔 |
| 화면 밖도 모두 그리기 데이터 작성 | 낭비 | **보이는 격자 칸의 개체만** 그리기 데이터에 넣는다(공간 격자 재사용) |

## 4. DOD 외에 계산량 자체를 줄이는 방법 (효과 큰 순)

### 4.1 무리 단위 표현 (가장 효과 큼)
- 멀리 있는 적은 한 마리씩 계산하지 않고 **"무리"(예: 50~200마리) 하나로 계산**한다. 무리는 위치·인원수·평균 체력만 가진다.
- 성벽이나 카메라 가까이 오면 무리를 **개별 적으로 풀어 준다.** 반대로 멀어지면 다시 묶는다.
- 화면에서는 무리 위치에 개별 그림을 흩뿌려 그리므로 **보이는 모습은 거의 같다.**
- 예: 적 5만 중 실제 개별 계산은 성벽 근처 5천~1만만. **CPU 계산이 수 분의 1로 줄어든다.**
- 게임 규칙(처치 수·보상·손실)은 무리의 인원수로 정확히 셀 수 있다.

### 4.2 화살 일제 사격(볼리) 단위
- 화살 한 발씩 날리지 않고 **분대 한 번의 일제 사격 = 화살 무리 하나**로 계산한다. 명중은 착탄 지점 주변 적에게 발 수만큼 나눠 적용한다.
- 화면에는 화살 몇 개만 그려 "많이 날아간다"는 느낌을 준다.
- 화살 계산 수가 수십 분의 1로 줄어든다. FirstRead의 "대량 원거리 공격" 느낌은 유지된다.

### 4.3 거리에 따라 업데이트 횟수 줄이기 (시간 분할)
- 성벽 근처는 매 프레임, 중간 거리는 2프레임마다, 먼 곳은 4프레임마다 이동·표적을 계산한다. 이동은 보간해서 부드럽게 보이게 한다.

### 4.4 표적 찾기 줄이기
- 아군 한 명씩 격자를 뒤지지 않고, **격자 칸마다 "가장 약한 적"을 한 번만 계산**해 두고 아군은 그 결과를 읽는다(D-019 규칙 유지).

### 4.5 애니메이션 단순화
- 먼 적은 걷기 프레임을 덜 자주 바꾸거나 1프레임 고정. 정면 시점이라 차이가 거의 안 보인다.

### 4.6 프레임 운영
- `Application.targetFrameRate = 60` 고정(120Hz로 돌리지 않기 — 발열 절반 가까이 줄어듦).
- 무거운 계산을 두 프레임에 나눠 처리(예: 격자·표적은 짝수 프레임, 투사체는 매 프레임).
- 발열 단계에 따라 내부 해상도·이펙트 수·먼 무리의 계산 빈도를 자동으로 낮추는 **품질 사다리**.

## 5. 현실적인 목표 제안 (추정)

| 방식 | 아이폰 14 Pro 예상 |
|---|---|
| 지금 구조 그대로, 6만 개별 계산 | 60Hz 유지 **어려움** (발열 시 30 근처로 추정) |
| 3장 그리기 개선 + 4.1 무리 표현 + 4.2 일제 사격 + 4.3 시간 분할 | **60Hz 가능성 있음** (개별 계산 1만 안팎 + 무리) — 실측 필요 |
| 보수적인 대안 | 모바일은 30Hz 고정 또는 규모를 1/3~1/5로 |

- 4.1·4.2는 **PC 버전에도 이득**이다(더 많은 적, 더 낮은 사양 지원 — D-020의 "낮은 사양 지원" 목표와 맞음). 모바일을 하지 않더라도 넣을 가치가 있다.
- 다만 4.1(무리 표현)은 **전투 규칙에 영향**을 준다(멀리 있는 적에게 쏜 화살이 어떻게 맞는지 등). 전투 설계(Battle.md)와 함께 정해야 한다.

## 6. 검증하려면 필요한 것

- **아이폰용 빌드는 Mac과 Xcode가 있어야 만들 수 있다.** 지금 작업 PC는 Windows다. Mac이 없으면 Unity 클라우드 빌드 같은 원격 빌드 서비스나 Mac 대여가 필요하다.
- 대안: 먼저 **안드로이드 고급 기기**로 같은 시험을 해 볼 수 있다(Windows에서 빌드 가능). 단 GPU 구조가 달라 아이폰 결과를 대신하지는 못한다.
- PerfLab에 이미 자동 측정(B)·빌드 메뉴가 있으므로, 모바일 빌드 대상만 추가하면 같은 방식으로 잴 수 있다. 측정은 **10~20분 연속 실행**으로 발열 후 성능까지 본다.
