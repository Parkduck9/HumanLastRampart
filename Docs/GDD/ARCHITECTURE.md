> **정하지 않는 것:** 전투 수치, 화면 디자인, 카메라 수치 같은 세부 설계. 이건 화면별 설계 문서에서 따로 다룬다.

## 1. 설계 원칙

1. **화면 하나 = 씬 하나 = 담당자 한 명.** 씬과 프리팹은 담당자만 수정한다 (RULES 9장).
2. **모듈끼리 직접 참조하지 않는다.** 모든 모듈은 `Core`만 참조하고, 서로 주고받는 데이터는 Core에 정의된 약속(데이터 클래스·인터페이스)으로만 전달한다. **예외:** Codex 화면 모듈(Frontend·Story·Meta)은 공용 UI 부품 `HLR.UI`도 참조한다 (CONTRACTS C-002, D-014).
3. **진행 상황은 하나의 데이터(`CampaignState`)에 모은다.** 전투는 이 데이터를 읽어 시작하고, 결과를 돌려준다. 정비 화면은 이 데이터를 고친다. 화면끼리 직접 값을 넘기지 않는다.
4. **정의 데이터와 진행 데이터를 분리한다.** 적·무기·함정의 기본 수치는 ScriptableObject(정의), 골드·병력·성벽 내구도 같은 진행 값은 일반 C# 데이터(진행)로 둔다 (RULES 9장 5번).
5. **1회차 완주에 필요한 만큼만 만든다.** 저장 기능, 다국어, 빌드 설정 등은 다음 마일스톤으로 미룬다 (12장).

## 2. 화면 흐름과 씬 구성

### 2.1 화면 흐름 (1회차 완주 기준)

```
[Boot] ──▶ [0 메인] ──시작──▶ [5 스토리] ──▶ [1·2 전투] ──승리──▶ [4 보상·손실] ──▶ [3 정비] ──▶ (다음 전투 또는 스토리)
              │설정 (메인 안의 팝업)       │패배
              └종료                         └──▶ [5 스토리: 패배 엔딩] ──▶ [0 메인] (처음부터)
```
- 패배 흐름은 CONTRACTS C-003 승인(D-014, C4 답변)으로 추가됐다.

### 2.2 씬 목록과 담당

| 씬 | 화면 | 담당 | 역할 |
|---|---|---|---|
| `Boot` | - | Claude (통합) | 게임 시작 시 한 번 열리고 계속 남는 씬. 화면 전환 관리자, 진행 데이터(`CampaignState`) 보관 |
| `MainMenu` | 0번 | Codex | 시작 / 설정 / 종료 |
| `Story` | 5번 | Codex | 캐릭터 + 대사 출력, 터치(클릭)로 넘김 |
| `Battle` | 1·2번 | Claude | 성벽 이동·병사 상호작용(1번), 지도·망원경 특수 공격(2번). **2번은 별도 씬이 아니라 전투 씬 안의 지도 모드**로 둔다(전투가 멈추지 않고 이어져야 하므로) |
| `Result` | 4번 | Codex | 보상, 잃은 병력 표시 |
| `Prep` | 3번 | Codex | 성벽 수리, 상점, 용병·군인 모집, 함정 설치 |

- **로딩 방식 제안:** `Boot`는 항상 열려 있고, 나머지 화면 씬은 하나씩 추가로 열고 닫는다(Additive). 화면을 바꿀 때 진행 데이터가 사라지지 않는다.

## 3. 모듈(어셈블리) 구성과 담당

| 모듈 (asmdef) | 담당 | 내용 | 참조 허용 |
|---|---|---|---|
| `HLR.Core` | Claude (**공용 경로**, 변경은 예약 필요) | 모듈 간 약속: 데이터 클래스, 인터페이스, 화면 ID, 간단한 서비스 등록소, 정의 데이터(SO) **클래스** | 없음 |
| `HLR.App` | Claude | Boot 씬, 화면 전환(GameFlow), 씬 로딩, `CampaignState` 보관 | Core |
| `HLR.Combat` | Claude | 성벽, 병사, 무기, 적, 웨이브, 표적 우선순위, 지도 모드, 함정 발동·피해 | Core |
| `HLR.Frontend` | Codex | 메인 화면, 설정 | Core, UI |
| `HLR.Story` | Codex | 스토리 재생(대사·캐릭터 표시, 패배 엔딩 포함) | Core, UI |
| `HLR.Story.Editor` | Codex | 스토리 제작 툴 (에디터 전용) | Core, Story |
| `HLR.Meta` | Codex | 보상·손실 화면, 정비 화면(수리·상점·모집·함정 배치) | Core, UI |
| `HLR.UI` | Codex (**공용 경로**) | 여러 화면이 같이 쓰는 UI 부품(버튼, 팝업, 폰트 설정) | Core |

```
                 ┌──────────── HLR.Core (약속) ────────────┐
                 ▲        ▲        ▲        ▲        ▲      ▲
              App      Combat   Frontend   Story    Meta    UI
           (Claude)  (Claude)  (Codex)   (Codex)  (Codex) (Codex)
                                            ▲
                                      Story.Editor (Codex)
```

- Frontend·Story·Meta → UI 참조는 CONTRACTS C-002 승인(D-014, C3 답변)으로 추가됐다. 위 그림은 Core 참조만 보여 준다.
- **금지:** 위 표에 없는 참조, 순환 참조. Combat이 Meta를 직접 부르는 식의 연결은 하지 않는다.
- `HLR.App`도 다른 모듈을 참조하지 않는다. 각 화면 씬에는 Core의 `IScreenEntry`를 구현한 진입 컴포넌트를 하나 두고, App은 씬 이름과 이 인터페이스만 안다.
- 화면 전용 UI(전투 HUD 등)는 각 모듈 안에 둔다. `HLR.UI`에는 둘 이상의 화면이 쓰는 것만 넣는다.

## 5. 화면 전환 방식 (C-003 후보)

- Core에 화면 ID와 전환 요청 인터페이스를 둔다.
  ```csharp
  // HLR.Core — 제안 예시 (확정 전, 이름과 형태는 바뀔 수 있음)
  public enum ScreenId { MainMenu, Story, Battle, Result, Prep }

  public interface IGameFlow {            // App(Claude)이 구현
      void GoTo(ScreenId next);
      CampaignState Campaign { get; }     // 진행 데이터 (6장)
  }

  public interface IScreenEntry {         // 각 화면 씬의 진입 컴포넌트가 구현
      ScreenId Id { get; }
      void OnEnter(IGameFlow flow);       // 화면이 열릴 때 App이 호출
      void OnExit();
  }
  ```
- 다음 화면을 정하는 규칙(예: 전투 후 결과 화면, 정비 후 다음 전투)은 App이 한 곳에서 관리한다. 각 화면은 "끝났다"만 알리고, 어디로 갈지는 App이 정하는 방식과 화면이 직접 `GoTo`를 부르는 방식 중 **하나를 선택**해야 한다 (Q-A3).
- **확정 (Q-A3, D-013):** 다음 화면은 **App 한 곳에서 정한다.** 각 화면은 끝났다는 신호만 보낸다. 신호의 형태(인터페이스 이름·메서드)는 C-003 초안에서 정한다.

## 6. 모듈 간 데이터 약속 (CONTRACTS 후보)

| 후보 | 이름 (제안) | 만드는 쪽 → 쓰는 쪽 | 내용 |
|---|---|---|---|
| C-001 | 폴더·씬 소유권 | 공통 | 2.2, 4장 표 |
| C-002 | 어셈블리 의존 방향 | 공통 | 3장 표와 그림 |
| C-003 | 화면 전환 | Claude(App) ↔ 모든 화면 | `ScreenId`, `IGameFlow`, `IScreenEntry` (5장) |
| C-004 | `CampaignState` 진행 데이터 | App 보관 / 모든 화면 읽기 | 현재 일차, 골드, 성벽 구간별 내구도, 병력 목록, 설치된 함정, 다음 전투 정보, 스토리 진행 위치 |
| C-005 | `BattleSetup` | Claude(App)가 `CampaignState`로 생성 → Combat | 이번 전투의 웨이브, 배치 병력, 함정 위치, 성벽 상태 |
| C-006 | `BattleResult` | Combat → Meta(4번) | 승패, 처치 수, 잃은 병력, 성벽 피해, 획득 보상, 사용한 함정 |
| C-007 | 결과 반영 규칙 | Meta(4번)가 `BattleResult`를 `CampaignState`에 반영 | 누가 언제 반영하는지 고정 (중복 반영 방지) |
| C-008 | 함정 경계 | Codex(배치·구매·저장) ↔ Claude(감지·발동·피해) | `TrapDef`(정의 클래스는 Core, 에셋은 Data/Traps), `TrapPlacement`(어디에 무엇을 설치했는지) |
| C-009 | 스토리 데이터와 종료 신호 | Codex(Story) → App | 대사·캐릭터·배경 데이터 형식, 스토리가 끝나면 다음 화면 신호 |
| C-010 | 정의 데이터 클래스 | Core에 클래스, 에셋은 각 Data 폴더 | `UnitDef`(병사·장교·주인공), `WeaponDef`, `EnemyDef`, `TrapDef`, `ItemDef` |
| C-011 | 표적 우선순위 설정 | Combat 내부 + 정비 화면 표시 여부 | FirstRead의 "체력 비율 낮음·높음·특수 적 먼저" 설정값을 진행 데이터에 저장할지 (Q-A5) |

- **약속 승인 순서:** C-001·C-002·C-003 → C-004·C-010 → C-005·C-006·C-007 → C-008·C-009·C-011.
- 승인 전까지 상대는 이 약속을 확정 API로 쓰지 않는다. 다만 화면 설계 문서 작성은 병행할 수 있다.

## 7. 전투 화면 구조 개요 (1·2번, Claude)

세부 설계는 Phase 1의 전투 설계 문서(`Docs/GDD/screens/Battle.md`)에서 다룬다. 여기서는 큰 덩어리만 적는다.

| 덩어리 | 내용 |
|---|---|
| 성벽(Wall) | 좌우로 긴 성벽을 여러 구간으로 나눔. 구간별 내구도. 주인공이 좌우로 이동 |
| 병사·포대(Defender) | 성벽 위 배치 지점. 활·석궁·대포·마법사 등. 상호작용 시 대포 설정과 표적 우선순위 지정(1번 화면) |
| 적·웨이브(Enemy/Wave) | 정면에서 다가오는 대규모 적. 일반 적 / 특수 적 |
| 표적 선택(Targeting) | 우선순위 규칙에 따라 공격 대상 선택 |
| 지도 모드(Tactical Map) | 2번 화면. 지도 펼치기, 특수 공격 지점 지정, 망원경(돋보기)으로 특수 적 확인 |
| 함정 발동(Trap) | 정비 화면에서 설치한 함정의 감지·발동·피해 |
| 카메라(Camera Rig) | 낮은 카메라, 캐릭터가 크게 보이는 구도(D-004). 투영 방식·각도·거리는 목업 비교 후 설정값으로 결정 |

- **성능 위험:** "1000마리"급 적을 2D 스프라이트로 처리하려면 개별 GameObject 대신 묶음 처리(풀링, 단순 이동 로직)가 필요하다. 1회차 완주는 적 1~2종, 적은 수로 시작하되 구조는 대량 처리를 막지 않게 만든다.
- **도트 표현 위험:** 원근 카메라에서는 도트가 흔들리거나 번질 수 있다. 카메라 목업에서 함께 확인한다.

| **Phase 1** 설계 | 아키텍처(이 문서), CONTRACTS 초안, 카메라 목업, 전투 설계 | 메인·스토리(+툴)·보상·정비 화면 설계 | Unity 프로젝트 생성, 설계 승인 |

| **Phase 3** 화면별 최소 구현 | 1·2번 전투 | 0번 → 5번 → 4번 → 3번 | 화면별 Play 확인 |
| **Phase 4** 통합 | 화면 연결, 1회차 완주 점검 | 연결 지원, 버그 수정 | 1회차 완주 검증 |
| **Phase 5** 다음 단계 | 유지보수 목록, 다음 마일스톤 제안 | 유지보수 목록 | 다음 범위 결정 |

- Phase 1에서 두 AI는 **서로 다른 문서**를 쓰므로 동시에 진행할 수 있다. 단, Codex의 화면 설계는 C-003·C-004 초안을 참고해야 하므로, Claude가 CONTRACTS 초안을 먼저 올린다.
- Phase 3에서 Codex의 화면은 전투 없이도 만들 수 있게, Claude가 Phase 2에서 **임시 `BattleResult`를 만드는 테스트용 진입 방법**을 함께 제공한다 (전투가 완성되기 전에 4번·3번 화면을 확인하기 위해).
