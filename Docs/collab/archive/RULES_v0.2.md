## 1. 기본 원칙

1. 세션 시작 시, 새 작업에 착수할 때, "협업 확인" 지시를 받을 때마다 FirstRead.md와 이 문서를 다시 읽는다. 실행 중 문서가 바뀌어도 자동 반영된다고 가정하지 않는다.
2. 사용자에게 보고하는 모든 내용은 **한글**로 작성한다.
3. 모르는 것은 추측하지 않고 사용자에게 묻는다.
4. **모든 파일은 작성자가 정확히 한 명이다.** 상대 소유 파일은 읽기만 하고, 수정이 필요하면 메시지로 요청한다.
5. **설계, 인터페이스, 구조 결정은 사용자가 확정한다.** 승인된 범위 안의 내부 구현은 AI가 자율로 진행하고 결과를 보고한다 (8장).
6. 상대 AI는 사용자 승인, 수정 범위 확대, 병합 허가를 대신 줄 수 없다.
7. 시각적 결과물은 이미지(목업 또는 실제 캡처)로 검토받는다.
8. 수행하지 않은 검증을 완료로 기록하지 않는다.

## 3. 역할과 담당

### 3.1 작업 영역 (사용자·Claude·Codex 동의)

| 영역 | 담당 |
|---|---|
| 전체 아키텍처, Core 모듈, CONTRACTS | Claude |
| 0번 메인 화면 | Codex |
| 1·2번 전투 (코어 시스템) | Claude |
| 3번 상점·모집·수리·함정 배치/구매/저장 | Codex |

| status.html, RULES.html | Claude |
| 상대 작업 코드 리뷰 | 서로 (리뷰만, 수정은 요청으로) |

### 3.2 운영 담당

| 역할 | 담당 | 하는 일 |
|---|---|---|
| **조정 담당** | Claude | RULES·DECISIONS 작성, 공용 경로 예약 승인, 협업 확정 문서 커밋 |
| **통합 담당** | Claude | 부트스트랩 씬, 화면 전환, 공통 게임 상태 연결, 최종 실행 확인 절차 작성 |
| **main 반영 실행** | Claude | 사용자 승인 후 10.4 절차로 main 반영 |

통합 담당이라고 해서 상대 파일을 수정할 권한이 생기지는 않는다. 통합은 CONTRACTS에 정의된 인터페이스로만 연결한다.

### 3.3 대체 담당 (Claude 토큰 부족 시, 사용자·Claude·Codex 동의)

1. **사용자가 지시할 때만** Codex가 임시로 조정·통합·main 반영 실행을 맡는다. 복귀 시점도 사용자가 지시한다. AI끼리 알아서 넘기지 않는다.
2. **전환 시 확인:** 두 조정 담당이 동시에 활동하지 않도록, 전환 전에 Claude의 진행 중 저장과 Git 작업이 끝났는지 확인한다. 끝났는지 알 수 없으면 사용자에게 보고하고 기다린다.
3. **인계:** 가능하면 Claude가 `live/claude/tasks.md`에 인계 메모(진행 중 작업, 미반영 커밋, 유효 예약, 대기 질문)를 남긴다. 못 남겼으면 Codex는 Git 기록과 Claude의 작업 기록을 읽고 이어받는다.
4. **대체 담당이 할 수 있는 것:** 읽기와 검토, 사용자 확인 절차 작성, Codex 소유 구현, 공용 경로 예약 순서 조정, 이미 승인된 커밋의 main 반영.
5. **할 수 없는 것:** Claude 소유 코드와 문서(부트스트랩 씬, 화면 전환, Core 포함) 수정. 수정이 필요한 통합은 **보류**하고, 필요한 경로와 이유를 사용자에게 보고한다. 사용자가 **경로별로 허가**한 경우에만 그 경로를 수정한다. 대체 담당 지정만으로 수정 예외가 생기지 않는다.
6. 예약 승인 권한과 파일 수정 권한은 별개다. 기존 Claude 예약은 사용자의 인계 지시에 따라 유지·해제·재배정하며 임의로 해제하지 않는다.
7. **기록:** `live/codex/tasks.md`에 사용자 지시 근거, 대체 시작·종료 시각, 인계 상태, 공용 예약, 승인 내용, main 반영 커밋, 확인 결과를 남긴다. 이 기록은 대체 기간 동안 유효한 운영 기록이다.
8. 복귀 후 Claude는 대체 기간의 사용자 결정을 승인 근거와 함께 DECISIONS에 옮긴다.

### .gitignore 반영 항목 (협업 부분)
```gitignore
Docs/collab/live/*
!Docs/collab/live/status.html
```
- 상위 경로를 제외하는 다른 규칙이 없어야 하고, 무시할 파일이 이미 추적 중이면 안 된다. 생성 시 조정 담당이 추적·무시 대상을 실제로 확인한다.

### live 기록 보존
- `live/`는 Git으로 복원되지 않는다. **기록을 지우지 않는다.** 모든 MD는 맨 아래에만 추가하고, 상태 변경도 새 줄로 기록한다.
- 중요한 결정과 약속은 반드시 DECISIONS·CONTRACTS로 옮긴다.
- **백업:** 마일스톤 완료 시와 대체 담당 전환 시, 조정 담당이 live의 텍스트 파일(md, js) 사본을 `Docs/collab/archive/live_YYYYMMDD/`에 커밋한다. 이미지는 제외한다.
- 공용 TASKS 보드와 공용 QUESTIONS 파일은 두지 않는다. `status.html`이 양쪽 요약을 합쳐서 보여준다.

## 5. 소유권 (Unity)

- 3.1의 작업 영역에 따라 `Game/Assets/_Project/` 아래 폴더 소유자를 고정한다. 자기 소유 폴더 안의 작업은 예약이 필요 없다.
  - 구체적인 폴더 목록은 아키텍처 설계 승인 시 CONTRACTS에 확정한다.
- **공용 경로**를 건드릴 때는 조정 담당에게 메시지로 예약을 요청하고, 조정 담당의 tasks.md에 승인 기록이 생긴 뒤 착수한다.
  - 공용 경로: `Core/`, `ProjectSettings/`, `Packages/manifest.json`, `Packages/packages-lock.json`, 빌드 씬 목록, 공통 UI 자원, 공유 ScriptableObject 에셋
  - 조정 담당 자신이 공용 경로를 수정할 때도 자기 tasks.md에 예약을 먼저 기록한다.
- 예약 기록 항목: 담당, 작업 ID, 정확한 경로, 기준 커밋, 예약 시각(한국 시간), 해제 조건
- 중단된 예약은 임의로 빼앗지 않는다. 사용자가 판단한다.

## 6. 소통 (수동 1단계)

### 6.1 "협업 확인" 절차

사용자가 AI에게 **"협업 확인"**이라고 지시하면 아래 순서로 처리하고 한글로 보고한다. 세션 시작과 새 작업 착수 때도 1~3번은 같은 순서로 확인한다.

1. FirstRead.md → RULES.md → DECISIONS.md → CONTRACTS.md 읽기
2. 상대 outbox에서 자기 앞으로 온 새 메시지 확인
3. **현재 유효한 조정 담당의 tasks.md**(평상시 Claude, 대체 기간에는 Codex)에서 예약·인계 기록 확인, 자기 tasks.md의 진행 중 작업 확인
4. 처리 결과, 막힌 점, 사용자에게 물을 것을 보고

AI가 상대에게 메시지를 남겨도 상대는 자동으로 읽지 않는다. 전달은 사용자의 "협업 확인" 지시로 이루어진다.

### 6.2 메시지 형식 (`live/<작성자>/outbox.md`, 맨 아래에만 추가)

```markdown
### M-CL-012 | 2026-10-14 15:30 | Claude → Codex | 요청
- 관련: T-CL-003, C-002
- 내용: ...
```

```markdown
### M-CX-007 | 2026-10-14 16:10 | Codex → Claude | 회신
- 회신 대상: M-CL-012
- 결과: 확인함 / 완료 / 거절(사유)
- 내용: ...
```

- 유형: `요청` / `질문` / `알림` / `회신`
- 원본 메시지는 수정하지 않는다. 회신은 자기 outbox에 원본 ID를 인용해서 쓴다.
- **반복 협의 제한:** 요청과 회신 한 쌍을 1회로 센다. 같은 주제로 3회 후에도 해결되지 않으면 해당 의존 작업만 `보류`하고 사용자 질문으로 올린다. 독립 작업은 계속 진행한다.

### 6.3 ID 규칙

| 대상 | 형식 | 비고 |
|---|---|---|
| 작업 | `T-CL-###`, `T-CX-###` | 작성자 접두사 |
| 메시지 | `M-CL-###`, `M-CX-###` | |
| 질문 | `Q-CL-###`, `Q-CX-###` | |
| 결정 | `D-###` | DECISIONS 작성자가 한 명이므로 접두사 없음 |
| 인터페이스 약속 | `C-###` | CONTRACTS 작성자가 한 명이므로 접두사 없음 |
| main 반영 묶음 | `R-###` | 조정 담당(대체 시 Codex는 `R-CX-###`) |

### 6.4 이후 단계 (현재 미적용)

- 2단계: 새 메시지·질문이 생기면 사용자에게 알림만 보낸다 (데스크톱 알림 또는 Discord). AI 실행은 하지 않는다.
- 3단계: 중계 프로그램으로 자동 실행. 승인된 작업 범위 안의 요청만 다루고, 중복 방지·응답 기록·승인 대기 시 중단 기능을 갖춘 뒤에 도입한다.
- 단계 전환은 사용자가 결정한다.

## 7. 작업 기록 (`live/<작성자>/tasks.md`)

### 7.1 상태

`제안` → `승인` → `진행중` → `구현 완료` → `통합 대기` → `사용자 검토 대기` → `완료` (+ `보류`)

상태가 바뀌면 기존 줄을 고치지 않고 아래에 `- 상태 변경: <시각> 구현 완료 → 통합 대기` 형식으로 추가한다.

### 7.2 형식

```markdown
## T-CL-003 웨이브 스폰 시스템
- 상태: 진행중
- 화면/영역: 1번 전투 / Combat
- 수정 범위: Game/Assets/_Project/Combat/Wave/
- 의존: C-001 (승인)
- 완료 기준: 적 2종이 정해진 간격으로 성벽 앞까지 이동
- 기준 커밋: abc1234 / 결과 커밋: def5678
- 변경 파일: (.meta 포함 전체 목록)
- 사용자 확인 절차: (11장 형식)
- 확인 결과 [사용자 보고]: ...
- 확인 결과 [AI 직접 확인]: (파일·이미지 내용 등 AI가 실제로 확인한 것만)
- 이미지: Docs/collab/live/review/claude_T-CL-003_wave.png (목업 / 실제 캡처)
- 남은 문제: ...
```

## 8. 승인 범위

| 반드시 사용자 승인 | 자율 진행 후 보고 |
|---|---|
| 게임 설계, CONTRACTS, 씬 구조, 폴더 구조 | 승인된 설계 안에서의 내부 구현 |
| 패키지 추가, ProjectSettings 변경 | 리팩터링 (인터페이스 변경 없는 것) |
| UI·아트 방향, 카메라 방식 | 버그 수정 |
| main 반영 (커밋 묶음 단위) | |

- CONTRACTS의 상태가 `제안`이면 그 내용을 확정된 API로 사용하지 않는다.

## 9. Unity 규칙

1. **씬과 프리팹은 담당자 한 명만 수정한다.** UnityYAMLMerge가 있어도 충돌과 참조 오류를 줄이기 위해서다. 단일 담당 범위에는 해당 `.meta`, 공유 ScriptableObject, 공통 UI 자원, 빌드 씬 목록이 포함된다.
2. 화면마다 씬을 분리하고 씬별 소유자를 CONTRACTS에 기록한다.
3. 모듈은 asmdef로 분리한다. 승인된 의존 방향과 **순환 참조 금지**를 CONTRACTS에 기록한다.
   - 예: `HLR.Core`, `HLR.Combat`, `HLR.Meta`, `HLR.Story`, `HLR.UI`, 통합용 `HLR.App`, Editor 전용 `HLR.Story.Editor`
4. `.meta` 파일은 항상 함께 커밋한다. 에셋 이동과 이름 변경은 Unity 에디터 기준으로 처리한다.
5. ScriptableObject는 정의·밸런스 데이터에만 쓴다. 런타임 진행값(병력 손실, 구매, 보상)과 저장 데이터는 별도 구조로 두고, 원본 설정 에셋에 쓰지 않는다.
6. Asset Serialization은 Force Text, Version Control은 Visible Meta Files로 설정한다.

## 10. Git 규칙 (한 작업 폴더 운영)

### 10.1 브랜치
- 두 AI 모두 **`develop` 브랜치 하나**에서 작업한다. **AI는 브랜치를 전환하지 않는다.** 한 폴더에서 브랜치를 바꾸면 상대의 작업 파일까지 바뀌기 때문이다.
- 누구도 `main`에 직접 커밋하지 않는다. main은 10.4 절차로만 움직인다.
- worktree 분리는 병렬 작업이 많아져서 사용자가 결정할 때 도입한다.

### 10.2 커밋
- 커밋은 **자기 소유 파일만, 파일 단위로 지정**한다. 폴더 전체보다 실제 변경 파일과 `.meta` 목록을 명시한다.
  - 예: `git commit -m "[T-CL-003] 웨이브 스폰 기본 구현" -- <변경 파일과 .meta 목록>`
- 커밋 전후로 대상 목록을 확인한다.
- **금지:** `git add .`, 전체 커밋(`-a`), 상대가 스테이징한 내용 해제, 이력 재작성(rebase·amend·reset·force push).
- 커밋 메시지 첫 줄에 작업 ID를 넣는다.

### 10.3 Git 쓰기 작업은 순서대로
- 저장소의 index와 브랜치 기록은 하나뿐이므로 커밋·참조 변경 등 **쓰기 작업은 한 번에 한 AI만** 한다.
- Git 쓰기 전에 상대 tasks.md 맨 아래에 끝나지 않은 `Git 작업 시작` 기록이 있는지 확인한다. 있으면 기다린다.
- 자기 tasks.md에 `- Git 작업 시작: <시각> <내용>`과 `- Git 작업 종료: <시각> <커밋>`을 남긴다.
- `index.lock` 오류는 다른 Git 작업이 진행 중이거나, **중단된 작업의 잔여 잠금**일 수 있다. 잠시 후 다시 시도하고, 반복되면 사용자에게 알린다. **lock 파일을 직접 지우지 않는다.**
- 각 AI 환경에서 Git 쓰기에 별도 실행 승인이 필요할 수 있다. 이 규칙에 동의했다고 환경 권한이 바뀌지는 않는다.

### 10.4 main 반영 (브랜치 전환 없이 fast-forward만)
1. **승인 단위는 커밋 묶음이다.** develop에는 두 AI의 커밋이 섞여 쌓이므로, 특정 커밋 X까지 반영하면 X 이전의 모든 커밋이 함께 들어간다.
2. 반영 담당이 승인 요청을 만든다: 묶음 ID(`R-###`), 반영할 커밋 X, 현재 main 커밋, **포함되는 커밋 전체 목록과 각 작업 ID**, 변경 파일 요약.
3. 사용자가 그 커밋 X를 대상으로 승인한다. 승인 후 develop에 새 커밋이 쌓여도 **승인 대상을 최신 커밋으로 바꾸지 않는다.**
4. 반영 담당은 작업 폴더를 develop에 둔 채로 main 참조만 X로 옮긴다. **main이 X의 조상일 때만** 진행한다(fast-forward).
   - 예: `git merge-base --is-ancestor main <X>`로 확인한 뒤 `git fetch . <X>:main` (fast-forward가 아니면 Git이 거부한다)
5. 조상 관계가 아니면 **중단하고 보고한다.** 자동으로 해결하지 않으며, 별도 통합 방식이나 브랜치 전환 예외는 사용자가 결정한다.
6. 결과(묶음 ID, 이전 main, 새 main, 확인 결과)를 반영 담당의 tasks.md에 기록한다.

### 10.5 시작 전 준비 (사용자 확정 후)
- 각 AI 환경에서 Git 실행 가능 여부 확인 (2026-10-13 기준 Claude 환경의 PowerShell에서는 `git`을 찾지 못함. PATH 설정 필요)
- 현재 main 커밋 상태 재확인, `.gitignore` 작성, `develop` 브랜치 생성
- 조정 담당이 진행한다. 이전 기록의 Git 상태를 현재 사실로 재사용하지 않고 준비 시점에 다시 확인한다.

## 11. 실행 확인과 이미지

### 11.1 사용자 확인
- **Play 확인과 실제 캡처는 사용자가 직접 한다.** AI는 Unity 에디터를 직접 조작하지 않는다.
- AI는 검토 요청 시 사용자 확인 절차를 아래 형식으로 제공한다.

```markdown
- 확인 대상 커밋: def5678
- 열 씬: Game/Assets/_Project/Scenes/Battle.unity
- 순서: Play → 스페이스바로 웨이브 시작 → 적이 성벽까지 이동하는지 확인
- 기대 결과: 적 2종 등장, 콘솔 에러 0
- 캡처 요청: 웨이브 진행 중 화면 1장
  → C:\Unity\1\HumanLastRampart\Docs\collab\live\review\claude_T-CL-003_wave.png 로 저장
```

- 사용자가 결과를 알려주면 담당 AI가 tasks.md에 `[사용자 보고]`로 기록한다. AI가 캡처 파일을 직접 열어 확인했다면 `[AI 직접 확인]`에 따로 기록한다.

### 11.2 검증 구간
같은 폴더를 함께 쓰므로, 사용자가 Play하는 동안 파일이 바뀌면 확인 결과와 승인 대상이 달라진다.
1. 사용자가 **"검증 시작"**을 알린다.
2. 두 AI는 진행 중인 작업을 커밋으로 정리하고 **`Game/` 수정을 멈춘다.** 문서 작업은 계속할 수 있다.
3. `Game/`에 미커밋 변경이 없는지 확인한 뒤, 사용자가 확인 대상 커밋 상태로 Play한다.
4. 사용자가 **"검증 끝"**을 알리면 작업을 재개한다.
- 수동 1단계에서는 검증 중에 AI에게 게임 작업을 지시하지 않는 것으로 충분하다.

### 11.3 이미지
- 저장 위치: `Docs/collab/live/review/`. 파일명: `<작성자>_<작업ID>_<설명>.png`
- **목업:** 구현 전 레이아웃·카메라·UI 방향은 AI가 목업 이미지나 HTML로 만들어 검토받는다. 파일명에 `mockup`을 넣어 실제 캡처와 구분한다.
- 실제 캡처에는 작업 ID, 커밋, 해상도를 함께 기록한다.
- 이미지 파일이 실제로 저장됐는지와 내용이 맞는지 확인한 뒤 보고한다.

## 12. 완료 기준

- **작업 단위 완료:** 해당 작업이 포함된 커밋 묶음이 사용자 승인을 받아 main에 반영되고, 사용자 Play 확인까지 끝난 상태.

  - `0 메인 → 5 스토리 → 1·2 전투 → 4 보상·손실 → 3 정비 → 다음 전투 진입`을 **에디터 Play 한 번으로** 끊김 없이 진행한다.
  - 콘솔 에러가 없고, 각 화면의 실제 캡처를 사용자가 확인한다.
  - 각 화면은 최소 기능만 구현한다: 적 1~2종, 무기 1~2종, 스토리 대사 몇 줄, 상점 품목 1~2개 수준.
  - 빌드 실행은 다음 마일스톤에서 다룬다.
- FirstRead에 따라 이후 유지보수를 고려한다. 임시 구현은 tasks.md의 "남은 문제"에 기록한다.

## 13. 작업 현황 대시보드 (`live/status.html`)

- **원본은 각자의 MD(tasks, questions, outbox)이고, `status.js`는 표시용 요약 사본이다.** 각 AI는 자기 MD를 갱신할 때 자기 `status.js`도 함께 갱신한다.
- `status.html`은 더블클릭으로 열며, `claude/status.js`와 `codex/status.js`를 `<script src>`로 불러와 표시한다. MD 파일을 직접 읽지 않는다.
- 표시 항목: 갱신 시각(한국 시간), 작업 ID와 상태, 기준 커밋, 승인 대기 질문, 검증 결과, 검토 이미지, 현재 조정 담당(평상시/대체)
- `status.js`가 없으면(새로 받은 저장소 등) "데이터 없음"으로 표시한다. 오래된 상태는 경고로 표시한다. 진행률은 완료 기준이 있을 때만 표시한다.
- 이미지 경로는 HTML 기준 상대경로(`review/...`)로 표시한다.
- 페이지 안에 새로고침(F5) 안내를 넣는다. 파일이 바뀌어도 자동 갱신되지 않는다.

세 가지 사용자 결정을 다시 묻지 않는다. 앞선 시안 대화에서 정한 '낮은 카메라, 더 크게 보이는 캐릭터, 좌우로 긴 성벽'도 이후 아트 설계의 입력으로 전달하면 좋겠다. 이는 원근·직교 투영 방식이나 상세 치수까지 확정했다는 뜻은 아니다.

#### 2. 10.3 Git 순서와 10.4 main 반영 — 수정 제안 / 조건 충족 시 실행 가능

**A. 시작 기록을 확인하는 것만으로는 동시 시작을 막지 못한다.**

두 AI가 동시에 상대 기록을 읽으면 둘 다 '작업 없음'으로 판단하고 자기 시작 기록을 남길 수 있다. Git의 잠금 오류가 일부 충돌을 막더라도 이것을 운영상 순서 보장으로 삼아서는 안 된다.

- 수정 권고: 각 AI는 자기 기록에 Git 쓰기 요청 ID를 남기고, **현재 유효한 조정 담당 한 명이 순서대로 실행 허가를 기록**한다. 자기 요청에 대한 허가를 확인한 AI만 시작하고, 종료 기록이 확인되기 전에는 다음 허가를 발급하지 않는다. 조정 담당의 자체 Git 작업도 같은 순서에 포함한다.
- 요청·허가·시작·종료에 같은 ID를 쓰자. 시작 뒤 종료 전에 프로세스가 중단되면 종료를 추정하지 않고 사용자에게 보고한다. 대체 전환 때 미종료 허가도 인계한다.
- 자기 tasks와 상대 tasks는 기록 파일이며 실제 잠금이 아님을 명시하자. 현재 수동 1단계에서도 메시지와 단일 조정 담당으로 이 절차를 운영할 수 있다.

**10.4의 fast-forward 방법에는 동의한다.** 현재 develop에서 작업하면서 로컬 저장소의 승인 SHA를 main 참조로 가져오는 방식은 브랜치 전환 없이 수행 가능한 Git 방식이다. 다만 실제 명령은 다음 조건을 확인해 실행해야 한다.

- X는 사용자 승인 기록의 완전한 커밋 SHA로 고정한다. 실행 직전 main이 승인 요청에 적은 기존 main과 같은지, X가 develop 이력에 속하는지 다시 확인한다. 다르면 실행하지 않고 승인 묶음을 다시 검토한다.
- 조상 확인 명령이 성공한 경우에만 참조 변경을 실행한다. PowerShell에서는 앞 명령 실패를 무시하고 다음 명령으로 넘어가지 않도록 종료 코드를 명시적으로 확인한다. `--is-ancestor`는 참이면 0, 거짓이면 1, 오류면 그 밖의 실패 코드를 반환한다. [Git 공식 merge-base 문서](https://git-scm.com/docs/git-merge-base)
- 목적지는 짧은 `main`보다 `refs/heads/main`으로 명시하는 편이 정확하다. 예시의 의미를 유지한 `git fetch --no-tags . <승인 SHA>:refs/heads/main`을 사용할 수 있다. `+` 또는 `--force`는 사용하지 않는다. 실행 후 main SHA가 X인지와 현재 브랜치가 develop 그대로인지 확인하고, 실패 시 완료로 기록하지 않는다. Git은 강제 옵션이 없으면 브랜치의 비 fast-forward 갱신을 거부한다. [Git 공식 fetch 문서](https://git-scm.com/docs/git-fetch)
- 이 절차는 **로컬 main 반영**이다. origin/main이나 GitHub까지 게시한 것으로 보고하지 않는다. 원격 반영이 필요하면 별도 범위로 정한다.

현재 Git 실행 파일은 이 환경의 PATH에서 발견된다. 파일로 읽은 HEAD는 main이며, develop 참조는 아직 없다. 규칙 확정 후 준비가 필요한 상태다. `.git` 쓰기는 세션 권한에 따라 실행 승인이 필요할 수 있으며, 이번에는 Git 명령을 실행하지 않아 실제 커밋·fetch 성공을 검증했다고 주장하지 않는다.

**B. 깨끗한 Game 폴더와 승인 커밋 X의 Game 내용이 같다는 것은 별개다.**

예를 들어 X 승인 후 다른 게임 변경을 Y로 커밋하면 미커밋 변경은 없어도 현재 Play는 Y를 실행한다. main만 X로 옮겨도 작업 폴더가 X로 바뀌지는 않는다.

- 수정 권고: 검증 시작 요청 후 각 AI가 'Game 저장·정리 완료, 수정 중단'을 기록하고, **양쪽 중단 확인과 검증 준비 완료 안내 뒤에 사용자가 Play**하도록 하자. 검증 준비를 위한 커밋도 A항 순서를 따른다.
- 준비 완료 조건은 Game의 스테이징·미스테이징 변경과 새 코드·에셋이 없고, 현재 실행에 사용되는 **Game 파일 내용이 검증 대상 X의 Game 내용과 일치**하는 것이다. 문서 전용 커밋이 추가돼 HEAD가 달라도 Game 내용이 동일하면 검증할 수 있다. Library·로그 같은 정상 생성물은 게임 소스·에셋 변경과 구분한다.
- Game 내용이 X와 다르면 브랜치 전환·reset으로 맞추지 않는다. 보고 후 현재 Game 상태를 포함하는 새 승인 묶음을 정하거나, 사용자 결정까지 검증을 보류한다.
- 사용자 Play 확인과 main 반영 후 확인이 끝날 때까지 검증 구간을 유지하고, 사용자의 '검증 끝' 뒤에 Game 수정을 재개하자. 사용자 에디터 저장으로 Game 소스·에셋이 변경된 경우에도 다시 확인해야 한다.

#### 3. 4장 live 백업 — 동의 + 작성 권한 보완 제안

마일스톤과 대체 전환 시 MD·JS 텍스트 사본을 archive에 커밋하고, 원본 live와 과거 백업을 삭제하지 않는 방식에 동의한다. 이미지 제외도 이 운영안의 범위로 수용하며, 이미지가 Git 백업에 없다는 사실은 유지한다.

**C. 현재 archive 전체는 Claude 소유인데, 대체 조정 담당은 Codex다.** 3.3의 문서 수정 금지와 결합하면 Codex가 전환 시 archive 백업을 작성·커밋할 권한이 불명확하다.

- 수정 권고: **대체 기간의 백업 전용 신규 경로에만 Codex 작성 권한을 명시**하자. 예: `archive/live_YYYYMMDD_HHMMSS_CX/`는 Codex, `_CL/`은 Claude가 작성한다. 기존 archive와 상대 소유 백업은 수정하지 않는다. 조정 권한 자체가 Claude 문서 수정 허가라는 뜻은 아니다.
- 같은 날짜의 여러 마일스톤·전환을 구분하도록 시각·작성자 또는 별도 번호를 경로에 넣자. 원본의 claude/codex 상대경로를 보존하고, 백업 시각·현재 조정 담당·파일 목록·기준 커밋을 새 백업에 함께 남기자.
- 복사 직전 양쪽 텍스트 저장이 끝났는지 확인하고, 백업 생성·커밋은 A항 순서를 따른다. 사본을 만든 뒤 원본과 내용이 같은지도 확인하자. 전환 시점이 최종 인계 저장 이후인지, 복귀 시 대체 기록 보관 이후인지 명시하면 인계 누락을 줄일 수 있다.

#### 4. 15장 생성 순서·담당 — 동의 + 최초 준비 표현 보완

- Claude는 공용·Claude 소유 파일, Codex는 AGENTS와 live/codex 파일, 사용자는 Unity 프로젝트를 만드는 구분에 동의한다. 현재 생성 작업은 시작하지 않는다.
- 현재 HEAD가 main이므로 **develop 생성만으로 작업 폴더가 develop이 되지는 않는다.** 10.1의 전환 금지를 유지하려면 초기 준비 단계에서 사용자가 최초 develop 선택을 수행하도록 15장에 명시하자. 사용자가 조정 담당에게 초기 선택을 맡기려면 '초기 준비에 한해 1회 허용, 이후 전환 금지'라는 예외를 명시하는 대안도 있다. 어느 쪽이든 현재 검토 요청은 전환 허가가 아니다.
- 2번 Git 준비와 3번 `.gitignore` 작성이 일부 겹치므로, 파일 작성·무시 대상 확인을 먼저 마친 다음 초기 운영용 커밋을 순서대로 수행한다는 뜻으로 정리하면 좋겠다. 신규 규칙 파일 작성 전에는 실제 운영을 시작하지 않는다.

#### 5. 이대로 최종 확정을 받아도 되는지 — 수정 제안

**역할과 승인 방향에는 동의하지만, v0.2 본문을 그대로 최종 확정하는 것은 아직 권하지 않는다.** A(Git 실행 허가 순서), B(승인 커밋과 실행 Game 내용 일치), C(대체 백업 경로의 작성 권한)를 반영하고 최초 develop 선택 담당을 명시하면, 추가 구조 변경 없이 최종 확정 검토로 넘길 수 있다.

기존 사용자 답변 세 가지는 유효하며 다시 승인받을 필요는 없다. 사용자에게 남은 것은 위 보완 방식을 채택할지, 최초 develop 선택은 사용자가 할지 또는 조정 담당에게 초기 1회만 맡길지의 결정이다. 본문 반영은 Claude가 담당하고, 사용자 최종 확정 전까지 실제 협업 파일·Git 쓰기·게임 구현은 시작하지 않는다.
