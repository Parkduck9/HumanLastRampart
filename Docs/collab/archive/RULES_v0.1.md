# Human Last Rampart 협업 규칙 (RULES)

- 상태: **초안 v0.1 (Codex 확인 대기 → 사용자 최종 확정 전)**
- 작성: Claude (조정 담당) / 작성일: 2026-10-13
- 근거: [`FirstRead.md`](../../FirstRead.md), [`PROPOSAL_Claude_to_Codex.md`](PROPOSAL_Claude_to_Codex.md)의 본문 + Codex 검토 의견 + Claude 재검토 + 사용자 답변(2026-10-13)
- 우선순위: **FirstRead.md > RULES.md > 기타 문서.** 충돌하면 상위 문서를 따르고 사용자에게 알린다.
- 이 문서는 확정 후 조정 담당(Claude)만 수정한다. 변경하려면 사용자 승인이 필요하다.

## 1. 기본 원칙

1. 세션 시작 시와 새 작업에 착수할 때마다 FirstRead.md와 이 문서를 다시 읽는다. 실행 중 문서가 바뀌어도 자동 반영된다고 가정하지 않는다.
2. 사용자에게 보고하는 모든 내용은 **한글**로 작성한다.
3. 모르는 것은 추측하지 않고 사용자에게 묻는다.
4. **모든 파일은 작성자가 정확히 한 명이다.** 상대 소유 파일은 읽기만 하고, 수정이 필요하면 메시지로 요청한다.
5. **설계, 인터페이스, 구조 결정은 사용자가 확정한다.** 승인된 범위 안의 내부 구현은 AI가 자율로 진행하고 결과를 보고한다 (8장).
6. 상대 AI는 사용자 승인, 수정 범위 확대, 병합 허가를 대신 줄 수 없다.
7. 시각적 결과물은 이미지(목업 또는 실제 캡처)로 검토받는다.

## 3. 역할과 담당

### 3.1 작업 영역

| 영역 | 담당 |
|---|---|
| 전체 아키텍처, Core 모듈, CONTRACTS | Claude |
| 0번 메인 화면 | Codex |
| 1·2번 전투 (코어 시스템) | Claude |
| 3번 상점·모집·수리·함정 배치/구매/저장 | Codex |

| 상대 작업 코드 리뷰 | 서로 (리뷰만, 수정은 요청으로) |

### 3.2 운영 담당

| 역할 | 담당 | 하는 일 |
|---|---|---|
| **조정 담당** | Claude | RULES·DECISIONS 작성, 공용 경로 예약 승인, 협업 문서 커밋 |
| **통합 담당** | Claude | 부트스트랩 씬, 화면 전환, 공통 게임 상태 연결, 최종 실행 확인 절차 작성 |
| **병합 실행** | Claude | 사용자 승인 후 `develop` → `main` 병합 실행 |

통합 담당이라고 해서 상대 파일을 수정할 권한이 생기지는 않는다. 통합은 CONTRACTS에 정의된 인터페이스로만 연결한다.

### 3.3 대체 담당 (Claude 토큰 부족 시)

1. **사용자가 지시할 때만** Codex가 임시로 조정·통합·병합 실행을 맡는다. AI끼리 알아서 넘기지 않는다.
2. 가능하면 Claude가 인계 메모(진행 중 작업, 미병합 내역, 대기 중 예약·질문)를 `live/claude/tasks.md`에 남긴다. 메모를 못 남겼으면 Codex는 Git 기록과 Claude의 작업 기록을 읽고 이어받는다.
3. 대체 기간에도 Codex는 **Claude 소유 코드와 문서를 수정하지 않는다.** 사용자가 따로 허가하면 예외다.
4. 대체 기간의 결정·병합 기록은 Codex가 `live/codex/tasks.md`에 남긴다. Claude가 복귀하면 조정 담당이 그 내용을 DECISIONS에 반영한다.
5. 복귀 시점도 사용자가 지시한다.

## 5. 소유권 (Unity)

- 3.1의 작업 영역에 따라 `Game/Assets/_Project/` 아래 폴더 소유자를 고정한다. 자기 소유 폴더 안의 작업은 예약이 필요 없다.
  - 구체적인 폴더 목록은 아키텍처 설계 승인 시 CONTRACTS에 확정한다.
- **공용 경로**를 건드릴 때는 조정 담당에게 메시지로 예약을 요청하고, 승인 기록이 생긴 뒤 착수한다.
  - 공용 경로: `Core/`, `ProjectSettings/`, `Packages/manifest.json`, `Packages/packages-lock.json`, 빌드 씬 목록, 공통 UI 자원, 공유 ScriptableObject 에셋
  - 조정 담당 자신이 공용 경로를 수정할 때도 자기 `tasks.md`에 예약을 먼저 기록한다.
- 예약 기록 항목: 담당, 작업 ID, 정확한 경로, 기준 커밋, 예약 시각(한국 시간), 해제 조건
- 중단된 예약은 임의로 빼앗지 않는다. 사용자가 판단한다.

## 6. 소통 (수동 1단계)

### 6.1 "협업 확인" 절차

사용자가 AI에게 **"협업 확인"**이라고 지시하면 아래 순서로 처리하고 한글로 보고한다.

1. FirstRead.md → RULES.md → DECISIONS.md 읽기
2. 상대 outbox에서 자기 앞으로 온 새 메시지 확인
3. 자기 tasks.md의 진행 중 작업과 예약 상태 확인
4. 처리 결과, 막힌 점, 사용자에게 물을 것을 보고

AI가 상대에게 메시지를 남겨도 상대는 자동으로 읽지 않는다. 전달은 사용자의 "협업 확인" 지시로 이루어진다.

### 6.2 메시지 형식 (`live/<작성자>/outbox.md`, 맨 아래에만 추가)

```markdown
### M-CL-012 | 2026-10-14 15:30 | Claude → Codex | 요청
- 관련: T-CL-003, C-002
- 내용: ...
```

```markdown
### M-CX-007 | 2026-10-14 16:10 | Codex → Claude | 회신
- 회신 대상: M-CL-012
- 결과: 확인함 / 완료 / 거절(사유)
- 내용: ...
```

- 유형: `요청` / `질문` / `알림` / `회신`
- 원본 메시지는 수정하지 않는다. 회신은 자기 outbox에 원본 ID를 인용해서 쓴다.
- **반복 협의 제한:** 요청과 회신 한 쌍을 1회로 센다. 같은 주제로 3회 후에도 해결되지 않으면 해당 의존 작업만 `보류`하고 사용자 질문으로 올린다. 독립 작업은 계속 진행한다.

### 6.3 ID 규칙

| 대상 | 형식 | 비고 |
|---|---|---|
| 작업 | `T-CL-###`, `T-CX-###` | 작성자 접두사 |
| 메시지 | `M-CL-###`, `M-CX-###` | |
| 질문 | `Q-CL-###`, `Q-CX-###` | |
| 결정 | `D-###` | DECISIONS 작성자가 한 명이므로 접두사 없음 |
| 인터페이스 약속 | `C-###` | CONTRACTS 작성자가 한 명이므로 접두사 없음 |

### 6.4 이후 단계 (현재 미적용)

- 2단계: 새 메시지·질문이 생기면 사용자에게 알림만 보낸다 (데스크톱 알림 또는 Discord). AI 실행은 하지 않는다.
- 3단계: 중계 프로그램으로 자동 실행. 승인된 작업 범위 안의 요청만 다루고, 중복 방지·응답 기록·승인 대기 시 중단 기능을 갖춘 뒤에 도입한다.
- 단계 전환은 사용자가 결정한다.

## 9. Unity 규칙

1. **씬과 프리팹은 담당자 한 명만 수정한다.** UnityYAMLMerge가 있어도 충돌과 참조 오류를 줄이기 위해서다. 단일 담당 범위에는 해당 `.meta`, 공유 ScriptableObject, 공통 UI 자원, 빌드 씬 목록이 포함된다.
2. 화면마다 씬을 분리하고 씬별 소유자를 CONTRACTS에 기록한다.
3. 모듈은 asmdef로 분리한다. 승인된 의존 방향과 **순환 참조 금지**를 CONTRACTS에 기록한다.
   - 예: `HLR.Core`, `HLR.Combat`, `HLR.Meta`, `HLR.Story`, `HLR.UI`, 통합용 `HLR.App`, Editor 전용 `HLR.Story.Editor`
4. `.meta` 파일은 항상 함께 커밋한다. 에셋 이동과 이름 변경은 Unity 에디터 기준으로 처리한다.
5. ScriptableObject는 정의·밸런스 데이터에만 쓴다. 런타임 진행값(병력 손실, 구매, 보상)과 저장 데이터는 별도 구조로 두고, 원본 설정 에셋에 쓰지 않는다.
6. Asset Serialization은 Force Text, Version Control은 Visible Meta Files로 설정한다.

## 10. Git 규칙 (한 작업 폴더 운영)

1. 두 AI 모두 **`develop` 브랜치 하나**에서 작업한다. **AI는 브랜치를 전환하지 않는다.** 한 폴더에서 브랜치를 바꾸면 상대의 작업 파일까지 바뀌기 때문이다.
2. 커밋은 **자기 소유 경로만** 대상으로 한다. 상대가 스테이징한 파일이 섞이지 않도록 경로를 지정해서 커밋한다.
   - 예: `git commit -m "[T-CL-003] 웨이브 스폰 기본 구현" -- Game/Assets/_Project/Combat/Wave/`
3. 커밋 메시지 첫 줄에 작업 ID를 넣는다.
4. `index.lock` 오류가 나면 상대가 Git 작업 중이라는 뜻이다. 잠시 후 다시 시도하고, **lock 파일을 직접 지우지 않는다.**
5. `main` 반영은 사용자 승인 후 병합 실행 담당(Claude, 대체 시 Codex)이 한다.
6. 협업 확정 문서(RULES·DECISIONS·CONTRACTS)는 조정 담당이 커밋한다.
7. worktree 분리는 병렬 작업이 많아져서 사용자가 결정할 때 도입한다.
8. 시작 전 준비: Git 설치·PATH 확인, `.gitignore` 작성, 초기 커밋, `develop` 브랜치 생성. 사용자 확정 후 조정 담당이 진행한다.

## 11. 실행 확인과 이미지

- **Play 확인과 실제 캡처는 사용자가 직접 한다.** AI는 Unity 에디터를 직접 조작하지 않는다.
- AI는 검토 요청 시 사용자 확인 절차를 아래 형식으로 제공한다.

```markdown
- 열 씬: Game/Assets/_Project/Scenes/Battle.unity
- 순서: Play → 스페이스바로 웨이브 시작 → 적이 성벽까지 이동하는지 확인
- 기대 결과: 적 2종 등장, 콘솔 에러 0
- 캡처 요청: 웨이브 진행 중 화면 1장 → review/claude_T-CL-003_wave.png 로 저장
```

- 사용자가 결과를 알려주면 담당 AI가 tasks.md에 기록한다.
- **목업:** 구현 전 레이아웃·카메라·UI 방향은 AI가 목업 이미지나 HTML로 만들어 검토받는다. 파일명에 `mockup`을 넣어 실제 캡처와 구분한다.
- 실제 캡처에는 작업 ID, 커밋, 해상도를 함께 기록한다.

## 12. 완료 기준

- **작업 단위 완료:** 사용자 검토 승인 + `main` 병합 + 병합 후 사용자 Play 확인
- **첫 마일스톤 "1회차 완주":**
  - `0 메인 → 5 스토리 → 1·2 전투 → 4 보상·손실 → 3 정비 → 다음 전투 진입`을 **에디터 Play 한 번으로** 끊김 없이 진행한다.
  - 콘솔 에러가 없고, 각 화면의 실제 캡처를 사용자가 확인한다.
  - 각 화면은 최소 기능만 구현한다: 적 1~2종, 무기 1~2종, 스토리 대사 몇 줄, 상점 품목 1~2개 수준.
  - 빌드 실행은 다음 마일스톤에서 다룬다.
- FirstRead에 따라 이후 유지보수를 고려한다. 임시 구현은 tasks.md의 "남은 문제"에 기록한다.

## 13. 작업 현황 대시보드 (`live/status.html`)

- 페이지 안에 새로고침(F5) 안내를 넣는다. 파일이 바뀌어도 자동 갱신되지 않는다.

#### 3. 4장 폴더·작성자·gitignore — 동의 + 보완 제안

- 전체 협업 경로가 현재 쓰기 허용된 `C:\Unity\1\HumanLastRampart` 아래라서, 규칙 확정 후 자기 소유 파일을 읽고 쓰는 방식은 이 환경에서 가능하다. 저장소 밖 공유 폴더의 추가 권한은 필요하지 않다. 단일 작업 폴더 운영에서는 양쪽이 같은 live 원본을 읽으므로 worktree 사본 문제도 없다.
- 제시한 두 gitignore 줄은 원리상 올바르다. live 자체가 아니라 바로 아래 항목을 제외하므로 `status.html`을 다시 포함할 수 있다. 단, 상위 경로를 제외하는 다른 규칙이 없고, 제외할 파일이 이미 추적 중이지 않아야 한다. 현재 `.gitignore`와 live 폴더는 없어 실제 적용 검증은 수행하지 않았다. 확정 후 생성 담당이 추적 대상과 무시 대상을 확인하자. [Git 공식 gitignore 문서](https://git-scm.com/docs/gitignore)

- 이미지 위치는 `Docs/collab/live/review/`로 통일하고, 11장의 캡처 저장 안내에는 전체 저장 경로를 적자. `review/...`는 HTML 표시용 상대경로로 유지한다.
- live는 Git으로 복원되지 않는다. 인계·예약·검증·캡처 기록을 지우지 않는 운영 규칙과 사용자 지정 백업 방식을 정하면 좋겠다. 대체 기간의 중요한 사용자 결정은 복귀 전까지 Codex 기록에만 있으므로 특히 보존해야 한다. status.html만 있는 새 checkout에서도 데이터 없음 상태를 보여주도록 하자.

#### 4. 10장 Git 규칙 — 기본 운영 동의 / main 반영 절차 수정 제안

- 한 폴더의 `develop`에서 자기 소유 경로만 커밋하고, 일상 작업 중 브랜치를 전환하지 않는 규칙은 지킬 수 있다. 새 파일은 자기 경로만 먼저 등록하고, 커밋 전후 대상 목록을 확인하며, `git add .`·전체 커밋·상대 스테이징 해제·이력 재작성은 하지 않는 방식으로 운영하자. 경로 지정 커밋은 다른 경로의 스테이징 내용을 제외하지만, 지정 경로의 작업 파일 내용이 대상이므로 폴더 전체보다 실제 변경 파일과 `.meta` 목록을 명시하는 편이 정확하다. [Git 공식 commit 문서](https://git-scm.com/docs/git-commit)
- 공유 index와 브랜치 기록은 하나이므로 **쓰기 Git 작업은 두 AI가 순서대로 수행**해야 한다. 공용 작업 기록에서 실행 담당·시작·종료를 확인하고 상대 작업 중에는 기다리자. `index.lock`은 동시 작업뿐 아니라 중단된 작업의 잔여물일 수도 있으므로 '상대 작업 중이라는 뜻'을 '다른 작업 또는 중단된 작업의 잠금일 수 있음'으로 수정하자. 반복되면 사용자에게 알리고 임의 삭제하지 않는다.
- **브랜치 전환 금지와 같은 폴더에서의 일반적인 develop → main 병합은 그대로는 양립하지 않는다.** 추천은 develop을 유지한 채, main이 승인된 develop 커밋의 조상일 때만 main을 해당 커밋으로 fast-forward 반영하는 절차를 따로 확정하는 것이다. 승인 커밋·기존 main 값·포함되는 전체 변경을 확인하고 조상 관계가 아니면 중단한다. 단순 참조 갱신이 조상 관계를 자동 보장하는 것은 아니다. 이력 분기가 생기면 사용자가 별도 통합 방식이나 브랜치 전환 예외를 결정해야 한다. [Git 공식 ref 갱신 문서](https://git-scm.com/docs/git-update-ref.html)
- 단일 develop에는 두 AI의 커밋이 누적되므로 특정 작업 하나의 승인만으로 그 시점의 전체 develop을 main에 반영하면 안 된다. **승인은 작업명뿐 아니라 main에 반영할 정확한 커밋과 포함 변경 전체를 대상으로** 받아야 한다. 커밋 후 상대가 이어서 커밋해도 승인 대상을 최신 HEAD로 바꾸지 않는다.
- 사용자 Play 확인은 승인된 커밋과 실제 작업 폴더 내용이 같아야 증거가 된다. 같은 폴더에 상대의 미커밋 코드·에셋이 남아 있으면 그것도 Unity 실행에 반영된다. 검토 시 양쪽 구현 변경을 잠시 멈추고, Game의 미커밋 변경이 없는 확인 구간을 잡자. main 반영 후에도 전환 없이 검증하려면 develop의 실행 내용이 승인 커밋과 같은 시점을 유지해야 한다.
- 현재 확인한 환경: Git 실행 파일은 PATH에서 발견되며, `.git/HEAD`는 main을 가리키고 main 참조에 커밋 값이 존재한다. develop 준비 완료로 간주하지 않는다. 이전 Claude 기록의 '커밋 없음 / Git 미검출'을 현재 사실로 재사용하지 말고 준비 시 다시 확인하자. 이번에는 Git 명령을 실행하지 않고 파일과 실행 파일 위치만 읽었다.
- 현재 세션 권한에서 `.git`은 읽기 허용 대상이다. 따라서 이후 Codex가 커밋·참조 변경 등 Git 쓰기를 수행할 때에는 별도 실행 승인이 필요할 수 있다. 협업 규칙 동의가 환경 권한을 자동으로 변경하지는 않는다. 지금은 준비·커밋·병합을 시도하지 않았다.

#### 5. 이전 의견의 반영 여부 — 대부분 동의 / 남은 보완

- 단일 작성자, 발신자별 회신, 접두사 ID, 공용 예약, 수동 전달 단계, 통합 담당, 상태 세분화, 함정 경계, asmdef 의존 방향, 설정과 런타임 데이터 분리, 이미지 상대경로는 반영됐다.
- worktree 대신 단일 폴더로 시작하는 변경은 사용자 선택을 반영한 운영안으로 수용한다. 이에 따라 남은 핵심 위험은 문서 사본이 아니라 공유 Git 상태와 미커밋 구현이 실행 검증에 섞이는 문제이며, 4항의 절차로 보완해야 한다.
- Play·실제 캡처를 사용자가 맡는 11장에 동의한다. AI가 아직 수행하지 않은 검증을 완료로 기록하지 않고, 사용자 보고 결과와 AI가 직접 확인한 파일·이미지 내용을 구분해 기록하자.
- 6.1은 자기 tasks만 확인하지만 공용 예약은 조정 담당 tasks에 있다. 세션 시작·새 작업 착수·협업 확인 모두 상대 outbox와 유효 조정 담당의 예약·인계 기록을 읽도록 명시해야 한다.
- 14장의 append-only와 '이전 기록에 대체 ID를 표기'는 엄밀히는 충돌한다. 과거 항목을 수정하지 않고 **새 결정에 '대체 대상: D-xxx'를 추가**하는 방식으로 통일하자.
- 15장은 '조정 담당 생성'과 '각자 자기 파일 작성'을 구분하자. Claude는 공용·Claude 소유 파일을, Codex는 AGENTS 및 codex 하위 파일을 생성한다. 초기 폴더 생성이 상대 소유 파일 작성까지 허용하는 것은 아니다.
- 개별 작업마다 main 반영을 완료 요건으로 유지하면 뒤따르는 미승인 develop 변경 때문에 완료가 대기할 수 있다. 초기에는 '구현 완료'와 '통합 대기'로 상태를 유지하고 승인된 묶음 단위로 main에 반영하는 운영을 권한다. 작업 단위 완료 정의 자체는 사용자 최종 결정대로 따른다.

#### 사용자에게 남은 질문

1. **main 반영:** 브랜치 전환 금지를 유지하고, 승인된 커밋까지 fast-forward 가능한 경우에만 main에 반영하는 방식으로 할까요? 이력이 분기되면 자동 해결하지 않고 보고하는 안을 추천한다.
2. **대체 통합:** 기본적으로 Claude 파일 수정이 필요한 통합은 보류하고, 필요한 경우 사용자가 경로별 예외를 허가하는 해석으로 확정할까요? 소유권 보호를 유지하는 이 방식을 추천한다.
3. **검증 구간:** 사용자 Play와 main 반영을 확인하는 동안 두 AI의 Game 수정을 잠시 멈추고, 미커밋 변경이 없는 승인 커밋을 함께 검증하는 방식에 동의할까요?

기존에 답한 엔진·플랫폼·역할 분담·수동 소통 등의 결정을 다시 묻는 것이 아니다. 위 질문은 초안의 실행 절차에서 남은 부분이며, 답하기 전까지 본문을 임의로 확정하거나 구현하지 않는다.
