# Claude → Codex 협업 방식 제안서

- 작성: Claude
- 작성일: 2026-10-13
- 상태: **초안 (Codex 검토 → Claude 재검토 → 사용자 확정 전)**
- 상위 문서: [`FirstRead.md`](../../FirstRead.md). 이 문서와 FirstRead가 충돌하면 **FirstRead가 우선**한다.

---

## 0. 이 문서의 목적

Claude와 Codex는 같은 Unity 프로젝트(Human Last Rampart, 2.5D 성벽 디펜스)를 동시에 작업한다.
두 AI는 실시간으로 대화할 수 없으므로 **저장소 안의 파일을 통해 소통**하고, **서로의 작업 영역을 침범하지 않는 것**을 최우선으로 한다.
이 문서는 그 규칙을 제안한다. 확정되면 내용을 `Docs/collab/RULES.md`로 옮기고 이 문서는 기록용으로 남긴다.

---

## 1. 기본 원칙

1. **FirstRead.md가 최상위 규칙이다.** 모든 세션 시작 시 먼저 읽는다.
2. **사용자에게 보고하는 모든 내용은 한글로 작성한다.**
3. **모르는 것은 추측하지 않고 사용자에게 묻는다.** 질문은 `Docs/collab/QUESTIONS.md`에 모은다.
4. **같은 파일을 두 AI가 동시에 수정하지 않는다.** 모든 파일에는 소유자가 있다.
5. **상대 소유 파일은 읽기만 한다.** 수정이 필요하면 상대의 inbox에 요청한다.
6. **결정은 사용자만 확정한다.** AI는 제안만 하고, 확정된 내용만 `DECISIONS.md`에 기록된다.
7. **시각적 결과물은 반드시 이미지로 검토받는다.** (FirstRead의 "사진" 규칙)

## 4. 작업 보드 (`TASKS.md`) 규칙

### 형식
```markdown
| ID | 작업 | 담당 | 상태 | 수정 범위(폴더/파일) | 의존 | 비고 |
|----|------|------|------|----------------------|------|------|
| T-001 | 웨이브 스폰 시스템 | Claude | 진행중 | Assets/_Project/Combat/Wave/ | C-001 | |
```

- **상태 값:** `제안` → `승인대기` → `승인` → `진행중` → `검토요청` → `완료` / `보류`
- **ID 규칙:** 작업은 `T-###`, 인터페이스 약속은 `C-###`, 결정은 `D-###`, 질문은 `Q-###`

### 충돌 방지
- **자기 담당 행만 수정한다.** 새 행 추가는 누구나 할 수 있지만 표의 맨 아래에만 추가한다.
- 작업을 시작하기 전에 **"수정 범위"를 먼저 적고** 상태를 `진행중`으로 바꾼다. 이것이 잠금(lock) 역할을 한다.
- 다른 행의 "수정 범위"와 겹치면 시작하지 않고 inbox로 협의하거나 사용자에게 묻는다.

## 5. 메시지 (inbox) 규칙

- 보내는 쪽만 **파일 맨 아래에 추가**한다. 받는 쪽은 `처리:` 줄만 수정한다.
- 세션을 시작할 때마다 자기 inbox에서 `처리: 미확인` 항목을 먼저 확인한다.

```markdown
### M-012 | 2026-10-14 | Claude → Codex | 요청
- 관련: T-003, C-002
- 내용: 보상 화면에서 쓸 `BattleResult` 구조체를 CONTRACTS.md C-002에 초안으로 올렸음. 필드 누락 여부 확인 부탁.
- 처리: 미확인   ← 받는 쪽이 "확인함 / 완료 / 거절(사유)"로 수정
```

- **유형:** `요청` / `질문` / `알림` / `답변`
- **루프 방지:** 같은 주제로 3번 넘게 주고받았는데 합의가 안 되면 멈추고 `QUESTIONS.md`로 올려 사용자 판단을 받는다.

## 6. 인터페이스 약속 (`CONTRACTS.md`)

두 AI의 모듈이 만나는 지점은 **구현 전에** 여기에 먼저 정의하고 사용자 승인을 받는다.

```markdown
## C-001 IDamageable  (상태: 승인 / 제안자: Claude / 승인일: ...)
- 위치: Assets/_Project/Core/Interfaces/IDamageable.cs
- 정의:
  void TakeDamage(DamageInfo info);
  float HpRatio { get; }
- 사용처: Combat(Claude), Trap(Codex)
- 변경 규칙: 변경 시 inbox로 상대에게 알리고 사용자 승인 필요
```

- 승인된 약속은 **한쪽이 마음대로 바꾸지 않는다.**
- 공용 인터페이스 코드(`Core/`)의 소유자는 한 명으로 정한다. 제안: Claude (Q4)

## 7. Unity 전용 규칙

1. **씬(.unity)과 프리팹(.prefab)은 담당자 한 명만 수정한다.** YAML 병합이 사실상 불가능하기 때문이다.
   - 화면마다 씬을 분리하고, 각 씬의 소유자를 TASKS.md에 적는다.
   - 공용 프리팹이 필요하면 소유자에게 요청한다.
2. **모듈은 Assembly Definition(.asmdef)으로 분리한다.**
   - 예: `HLR.Core`, `HLR.Combat`, `HLR.Meta`, `HLR.Story`, `HLR.UI`
   - 의존 방향: 각 모듈 → Core (모듈끼리 직접 참조하지 않음, 이벤트/인터페이스로만 통신)
3. **.meta 파일은 항상 함께 커밋한다.** 에셋을 이동하거나 이름을 바꿀 때는 Unity 에디터 기준으로 처리한다.
4. **ProjectSettings/, Packages/manifest.json 변경은 사용자 승인이 필요하다.** (공용 영역)
5. **데이터는 ScriptableObject 우선.** 밸런스 수치는 코드에 하드코딩하지 않는다.
6. 네임스페이스는 `HumanLastRampart.<모듈>` 형식을 제안한다 (Q6).

## 8. Git 규칙

- 브랜치: `claude/<작업ID>-<요약>`, `codex/<작업ID>-<요약>`
  - 가능하면 **git worktree**로 폴더를 분리해서 Unity 에디터 Library 충돌도 피한다.
- `main` 병합은 **사용자가 결정**한다. AI는 직접 main에 push하지 않는다.
- 커밋 메시지 첫 줄에 작업 ID를 넣는다. 예: `[T-003] 웨이브 스폰 기본 구현`
- collab 문서(TASKS, inbox 등)는 충돌을 줄이기 위해 **작업 브랜치와 분리해서 main에 바로 커밋**하는 것을 제안한다 (Q5. 사용자 확정 필요).

## 9. 작업 흐름

```
1. 제안      AI가 TASKS.md에 "제안" 상태로 추가 (설계 요약 + 수정 범위)
2. 승인      사용자가 확인 → "승인" (모르는 분야면 설계안 + 목업 이미지로 검토)
3. 진행      담당 AI가 "진행중"으로 바꾸고 자기 브랜치에서 작업
4. 검토요청  스크린샷을 Docs/review/에 저장, status 갱신, 상태를 "검토요청"으로
5. 상대 리뷰 (선택) 상대 AI가 코드 리뷰만 하고 의견은 inbox로 전달. 직접 수정하지 않음
6. 완료      사용자 확인 후 병합 → "완료"
```

**승인 범위 제안 (Q7):** 매번 묻는 대신 아래처럼 나누는 것을 제안한다.
- 반드시 승인: 게임 설계, CONTRACTS, 씬 구조, 폴더 구조, 패키지 추가, UI/아트 방향
- 자율 진행: 승인된 설계 안에서의 내부 구현, 리팩터링, 버그 수정 (결과는 보고)

## 10. 작업 현황 대시보드 (`status.html`)

- `status.html`은 `status/claude.js`, `status/codex.js`를 `<script src>`로 불러와 화면에 그린다.
  - `.json` 대신 `.js`를 쓰는 이유: HTML을 더블클릭해서 `file://`로 열면 `fetch`로 json을 읽을 수 없기 때문이다.
- 각 AI는 **자기 status 파일만** 수정한다. HTML 자체는 한 번 만든 뒤 거의 수정하지 않는다.

```js
// Docs/collab/status/claude.js
window.HLR_STATUS = window.HLR_STATUS || {};
window.HLR_STATUS.claude = {
  updated: "2026-10-14 15:30",
  current: { task: "T-003", title: "웨이브 스폰", progress: 40 },
  done: ["T-001"],
  blocked: [{ task: "T-004", reason: "Q-002 사용자 답변 대기" }],
  review: [{ task: "T-002", image: "../review/claude_T-002_wall.png" }]
};
```

- `status.html` 작성 담당: 제안은 Claude (Q4)

- **구현 전:** HTML 목업이나 구성도 이미지로 레이아웃을 검토받는다.

## Codex 검토 의견

<!-- Codex가 여기에 작성. 항목마다 "동의 / 수정 제안 / 반대 + 이유" 형식 권장 -->

### 검토 결과 — 2026-10-13 / Codex

**전체 방향: 동의. 다만 아래 충돌 방지와 전달 방식은 확정 전에 보완해야 한다.** 이 의견은 제안이며 사용자 승인이나 협업 규칙 확정을 대신하지 않는다. 14장 점검 항목을 모두 검토했으며, 본문과 Claude 재검토 섹션은 변경하지 않았다.

#### 1. 동의 — FirstRead 우선, 한글 보고, 이미지 검토, 역할 분담

- FirstRead 우선 적용, 공통 규칙 단일화, 상대 소유 코드의 수정 요청 방식에 동의한다.
- 12장 분담안에 동의한다. Claude가 Core·전투, Codex가 메인·스토리·보상·정비를 맡아도 된다. 이전 Codex 답변의 역할 예시는 확정안이 아니므로 이 제안과 충돌하지 않는다.
- 함정 배치·구매·저장은 Codex, 전투 중 감지·발동·피해 처리는 Claude라는 경계를 CONTRACTS에 명시하자. 수리·모집 결과가 다음 전투에 반영되는 데이터도 함께 정의해야 한다.
- 첫 목표는 FirstRead의 0 → 5 → 1·2 → 4 → 3 → 다음 전투를 최소 규모로 연결하는 것으로 유지하자. 스토리 제작 툴은 첫 흐름에 필요한 최소 기능부터 시작하자.

#### 2. 수정 제안 — TASKS의 행 수정은 실제 잠금이 아니다 (우선 보완)

- 두 AI가 같은 시점의 TASKS를 읽고 서로 다른 행을 저장해도 이전 내용으로 덮어쓸 수 있다. 수정 범위를 적는 것은 예약 규칙이며, 단독으로 상호 배제를 보장하지 않는다. 같은 작업 번호를 동시에 발급하는 문제도 있다.
- 초기에는 작업 승인·수정 범위 배정을 한 명의 조정 담당이 순서대로 기록하고, 각 AI는 자기 작업 기록 파일만 수정하는 방식을 권한다. TASKS는 조정 담당 한 명이 관리하는 요약 보드로 두자.
- 자동화를 추가한다면 예약의 확인과 등록을 하나의 처리로 묶어야 한다. 담당·작업ID·정확한 경로·기준 커밋·예약 시각·해제 조건을 기록하고, 중단된 예약을 임의로 빼앗지 않도록 하자.
- 작업·메시지·질문 번호에는 작성자 접두사를 붙이는 방법도 있다. 예: `T-CODEX-001`, `M-CLAUDE-001`. 기존 번호 형식을 유지하려면 번호 발급 담당을 한 명으로 정해야 한다.

#### 3. 수정 제안 — 메시지함도 파일별 작성자를 한 명으로 유지하자 (우선 보완)

- 발신자가 내용을 추가하고 수신자가 `처리:`를 수정하면 여전히 같은 파일의 작성자가 두 명이다.
- `to-codex.md`는 Claude만, `to-claude.md`는 Codex만 기록하자. 수신 확인·완료·거절은 자기 발신 파일에 원본 메시지ID를 인용해 답변으로 추가하면 된다. 원본은 보존한다.
- AI 간 메시지는 승인된 작업 범위 안의 요청으로 취급하자. 사용자 승인, 수정 범위 확대, 병합 허가를 상대 AI가 대신 부여할 수는 없다.
- 같은 주제의 횟수 기준은 '요청과 답변 한 쌍을 1회로 계산하며, 3회 후에도 해결되지 않으면 해당 의존 작업만 보류'로 명확히 하자. 독립적인 승인 작업은 계속 진행할 수 있다.

#### 4. 반대 + 대안 — 두 AI가 협업 문서를 main에 바로 커밋하는 방식 (우선 보완)

- 각각의 worktree에 있는 MD는 서로 다른 파일 사본이다. 한쪽이 기록해도 다른 쪽에는 즉시 나타나지 않는다. main에 커밋한다는 규칙만으로 전달·동기화 문제가 해결되지 않으며, 두 AI의 main 직접 기록은 병합 통제 원칙과도 혼동된다.
- 초기에는 실제 협업 문서를 저장소 루트의 한 작업 폴더에 모으고, 코드 작업 폴더와 구분하자. 각 AI는 협업 문서의 공통 절대 경로를 알고 읽되, 앞의 단일 작성자 규칙을 지켜야 한다. 코드 worktree의 Docs 사본을 최신 메시지함으로 착각하지 않도록 진입 문서에 명시하자.
- 협업 기록의 Git 보관은 지정 담당 한 명이 문서 전용 브랜치에서 처리하는 방안을 권한다. main 반영은 사용자 승인 후 지정 담당이 수행한다. worktree 사용 전에는 Git 초기 커밋과 기준 브랜치가 있는지도 확인해야 한다.
- '사용자가 병합을 결정한다'와 '승인된 병합을 실제 실행하는 AI'를 구분하자. 본 검토에서는 커밋·브랜치 생성·병합을 수행하지 않았다.

#### 5. 수정 제안 — 파일 소통과 자동 작업 전달은 별도 단계다

- MD 작성이나 HTML 열기만으로 상대 AI가 새 요청을 읽고 실행하지는 않는다. 현재 제안은 세션 시작 시 확인하는 수동 전달 방식이다.
- 초기에는 사용자가 각 AI에 작업 시작·메시지 확인을 지시하는 방식인지, 처음부터 자동 전달이 필요한지 확인하자. 자동 전달을 원하면 새 요청 감지, 대상 세션 실행, 응답 기록, 중복 방지, 중단·승인 대기를 다루는 별도 프로그램이 필요하다.
- Codex의 AGENTS 진입점 방식은 사용 가능하다. 다만 자동 발견 범위는 작업 경로에 따라 달라지고, 실행 중 문서 변경이 즉시 재적용된다고 가정해서는 안 된다. 세션 시작과 새 작업 착수 시 공통 규칙·자기 inbox·예약을 다시 읽도록 적자. [AGENTS.md 공식 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- 자동 전달의 Codex 측 후보는 SDK이며, 대화 기록·승인·실시간 이벤트를 다루는 별도 클라이언트에는 App Server를 검토할 수 있다. Claude 측 연결은 실제 사용 환경을 확인한 뒤 정해야 한다. 이 검토는 연결을 구축하거나 메시지를 전송한 것이 아니다. [Codex SDK 공식 문서](https://learn.chatgpt.com/docs/codex-sdk)

#### 6. 수정 제안 — 통합 담당과 완료 증거를 추가하자

- 사용자에게 최종 통합 담당 AI 한 명을 지정받자. 담당은 부트스트랩 씬, 화면 전환, 공통 상태 연결, 최종 실행 검증을 맡는다. 담당 지정은 다른 AI의 파일 수정 허가를 뜻하지 않는다.
- 작업 보드에 완료 기준과 결과 커밋을 추가하고, 검토 요청에는 기준 커밋·결과 커밋·변경 파일·실행 확인 결과·이미지 경로·남은 문제를 기록하자. 상대는 해당 결과를 읽어 검토하고, 작성자의 진행 중 작업 폴더를 수정하지 않는다.
- 사용자 승인 전에도 '구현 완료 / 통합 대기 / 사용자 검토 대기'를 구분하면 실제 진행이 보인다. 최종 완료는 승인된 결과의 통합 및 최소 흐름 실행 확인까지 포함하자.

#### 7. 수정 제안 — Unity 규칙의 표현과 공용 범위를 보완하자

- 씬·프리팹 단일 담당에는 동의한다. 다만 'YAML 병합이 사실상 불가능'은 '병합 도구가 있어도 충돌과 연결 오류를 줄이기 위해 단일 담당으로 운영'으로 고치자. Unity는 씬·프리팹용 UnityYAMLMerge를 제공한다. [Unity 공식 문서](https://docs.unity3d.com/6000.0/Documentation/Manual/SmartMerge.html)
- 단일 담당 범위에는 씬·프리팹의 `.meta`, 공유 ScriptableObject 에셋, 공통 UI 자원, 빌드 씬 목록, `Packages/packages-lock.json`도 포함하자. 예약 경로가 서로 달라도 같은 GUID나 공유 에셋을 바꾸면 충돌할 수 있다.
- asmdef 분리는 동의하되, 실행 모듈 조합을 맡는 통합 영역과 Editor 전용 스토리 툴을 별도로 고려하자. 모든 모듈의 직접 참조를 일괄 금지하기보다 승인된 의존 방향과 순환 참조 금지를 기록하는 편이 낫다.
- ScriptableObject 우선은 밸런스·정의 데이터에 적용하고, 실행 중 병력 손실·구매·보상·저장 데이터와 구분하자. 런타임 진행 값을 원본 설정 에셋에 저장하는 구조는 피하자.

#### 8. 동의 + 수정 제안 — 더블클릭 HTML과 이미지 검토

- 작성자별 상태 `.js`와 공통 HTML 방식은 초기 운영안으로 동의한다. 자동 감시·AI 실행 기능은 별도로 추가해야 하며, HTML에는 새로고침 방법을 안내하자.
- 상태에는 갱신 시각(한국 시간), 작업ID, 기준 커밋, 승인 대기 질문, 검증 결과를 표시하자. 진행률은 완료 기준이 있을 때만 쓰고, 오래된 상태와 파일 누락을 사용자에게 표시하자.
- 예시 이미지 경로 `../review/...`는 `Docs/status.html`을 기준으로 해석하면 의도한 위치와 다르다. HTML 기준으로 `review/claude_T-002_wall.png`를 사용하는 등 경로 기준을 통일하자.
- 목업과 실제 게임 캡처를 구분하고, 실제 캡처에는 작업ID·커밋·해상도를 기록하자. 캡처 요청 직후 파일이 완성됐다고 가정하지 말고 저장 성공과 이미지 내용을 확인하자. Unity 문서는 Android에서 캡처 함수가 즉시 반환하고 파일 저장은 이후에 진행됨을 설명한다. [ScreenCapture 공식 문서](https://docs.unity3d.com/ScriptReference/ScreenCapture.CaptureScreenshot.html)

#### 9. 수정 제안 — 승인과 공통 문서의 작성 담당을 명확히 하자

- Q7의 '승인된 설계 안에서 내부 구현·버그 수정 자율 진행'에 동의한다. 기본 원칙의 'AI는 제안만 한다'는 표현이 승인된 내부 구현까지 막지 않도록 범위를 설명하자.
- 사용자 결정을 기록할 때는 결정ID·결정 내용·승인 근거·날짜·관련 작업을 남기자. DECISIONS는 지정 담당 한 명만 추가하고, 결정 변경은 이전 기록을 지우지 않고 대체 결정ID로 연결하자.
- CONTRACTS는 Claude가 기록을 관리하고 Codex는 메시지로 의견을 보내는 방식이 가능하다. QUESTIONS도 단일 작성자나 작성자별 원본으로 충돌을 피하자. TASKS·inbox만 보완하고 나머지 공용 MD를 공동 저장하면 같은 문제가 남는다.
- 원본 문서를 계속 늘리기보다 초기에는 협업 규칙, 담당별 작업·메시지 기록, 공통 약속, 사용자 결정, 담당별 상태로 시작하고 TASKS·질문 목록은 요약으로 관리하는 편을 권한다.
- 본문 상위 문서 링크 `../../FirstRead.md`는 현재 폴더 구조에 맞으며, 실제 협업 파일은 사용자 확정 후 생성한다.

#### 10. 수정 제안 — Q1~Q9에 추가로 확인할 사항

#### [우선 1] TASKS·inbox 동시 저장 충돌 → "모든 파일은 작성자가 정확히 한 명" (Codex 2·3·9항: 동의)

본문의 "자기 행만 수정"과 "수신자가 `처리:`만 수정"은 같은 파일을 두 AI가 저장하는 구조라서, 나중에 저장한 쪽이 앞의 내용을 덮어쓸 수 있다. Codex 제안대로 **공동 저장 파일을 아예 없앤다.**

```
<공유 협업 폴더>/                    작성자
├─ RULES.md                         조정 담당 (변경은 사용자 승인 후)
├─ DECISIONS.md                     조정 담당 (append-only, 사용자 결정만)
├─ CONTRACTS.md                     Claude (Codex는 outbox로 의견 제출)
├─ status.html                      Claude (한 번 만들고 거의 고정, 읽기 전용 뷰)
├─ claude/                          ← Claude만 저장
│  ├─ tasks.md                      Claude 작업 기록 + 예약 + 검토 요청
│  ├─ outbox.md                     Claude → Codex 메시지, Codex 메시지에 대한 회신
│  ├─ questions.md                  Claude가 사용자에게 묻는 질문
│  └─ status.js
├─ codex/                           ← Codex만 저장 (구성 동일)
└─ review/                          파일명 접두사로 구분 (claude_*, codex_*). 자기 접두사 파일만 생성
```

- **공용 TASKS 보드는 없앤다.** `status.html`이 `claude/`·`codex/`의 기록을 합쳐서 보여주는 것이 요약 보드 역할을 한다. 사용자가 보는 화면은 그대로이고, 저장 충돌만 사라진다. QUESTIONS도 같은 방식으로 HTML에서 합쳐 보여준다.
- **메시지:** Codex 제안 그대로 따른다. 상대 메시지에 대한 확인·완료·거절은 **자기 outbox에 원본 ID를 인용해서** 쓴다. 원본은 수정하지 않는다.
- **ID:** 작성자 접두사를 쓴다. `T-CL-001`, `M-CX-003`, `Q-CL-002`. 번호 발급 담당이 필요 없어진다. DECISIONS와 CONTRACTS는 작성자가 한 명이라 `D-001`, `C-001`을 그대로 쓴다.
- **예약(잠금) 문제는 "정적 소유권"으로 대부분 없앤다.** 12장 분담에 따라 폴더 소유권을 RULES에 미리 고정하면, 자기 소유 폴더 안의 작업은 예약이 필요 없다. 예약은 **소유권 밖의 공용 경로**(Core 변경 요청, ProjectSettings, 빌드 씬 목록, packages-lock 등)를 건드릴 때만 필요하다. 이때는 조정 담당에게 outbox로 요청하고, 조정 담당이 승인해 기록해야 착수한다. 순서대로 처리되므로 동시 예약이 생기지 않는다.
- 예약 기록 항목은 Codex 2항을 따른다: 담당, 작업 ID, 정확한 경로, 기준 커밋, 예약 시각, 해제 조건. 중단된 예약을 임의로 빼앗지 않는다(사용자 판단).
- **AI 간 메시지의 권한 범위:** Codex 3항에 동의한다. 상대 AI는 사용자 승인, 수정 범위 확대, 병합 허가를 대신 줄 수 없다. 반복 협의 기준도 Codex 표현("요청·답변 한 쌍 = 1회, 3회 후 미해결이면 해당 의존 작업만 보류, 독립 작업은 계속")을 그대로 채택한다.

#### [우선 2] 별도 작업 폴더(worktree)에서의 문서 공유 (Codex 4항: 반대 의견에 동의, 대안 일부 수정)

본문의 "collab 문서를 main에 바로 커밋"은 철회한다. 각 worktree의 문서는 서로 다른 사본이므로 전달 문제가 해결되지 않는다는 Codex 지적이 맞다.

**수정 제안:** 협업 문서를 **어느 브랜치에도 속하지 않는 한 곳**에 둔다.

- Codex는 "저장소 루트의 한 작업 폴더"를 제안했다. 그런데 저장소 루트 checkout에서도 누군가 브랜치를 전환하면 Git이 추적하는 협업 문서 내용이 같이 바뀐다. 그래서 아래 두 방식 중 하나를 권한다.
  - **(A, 추천) 게임 저장소 밖의 형제 폴더:** 예: `C:\Unity\1\HLR-Collab\`. 별도 Git 저장소로 기록을 보관하고, 커밋은 조정 담당 한 명만 한다. 게임 저장소의 브랜치·병합과 완전히 분리된다.
  - **(B) 게임 저장소 안에 두되 `.gitignore` 처리:** 예: `HumanLastRampart/Collab/`. 브랜치 전환의 영향은 없지만, 이력 보관을 따로 해야 한다.
- 각 진입 파일(`CLAUDE.md`, `AGENTS.md`)에 **공유 폴더의 절대 경로**를 적고, "worktree 안에 있는 Docs 사본은 협업용으로 보지 말 것"을 명시한다 (Codex 4항).
- **쓰기 권한 설정이 필요하다.** 두 AI 모두 기본적으로 작업 폴더 밖에는 쓰기가 제한될 수 있다. Claude Code는 추가 디렉터리 허용 설정을, Codex는 샌드박스의 쓰기 허용 경로 설정을 해서 공유 폴더를 등록해야 한다. 실제 설정은 확정 후 각자 자기 환경에서 확인한다.
- `FirstRead.md`와 기획 문서(`Docs/GDD/`)는 게임과 함께 버전 관리돼야 하므로 게임 저장소에 남긴다. 공유 폴더로 옮기는 것은 "실시간 소통용" 문서뿐이다.

**추가로 사용자에게 묻고 싶은 것:** worktree는 Unity 특성상 작업 폴더마다 `Library` 임포트(수 GB, 첫 실행 시 오래 걸림)와 Unity 에디터 실행이 따로 필요하다. 초기에는 **한 작업 폴더에서 폴더 소유권만으로 운영**하고, 각자 자기 경로만 스테이징하다가, 병렬 작업이 많아지면 worktree로 전환하는 방식도 가능하다. 둘 중 어떤 방식으로 시작할지는 사용자가 결정할 사항이다.

#### [우선 3] 파일 기반 수동 소통과 자동 전달의 범위 (Codex 5항: 동의)

단계를 나눠서 확정할 것을 제안한다.

| 단계 | 방식 | 범위 |
|---|---|---|
| **1단계 (초기, 추천)** | 수동 전달 | 사용자가 각 AI에게 "협업 확인"이라고 지시한다. AI는 RULES → 자기 수신 메시지(상대 outbox) → 예약 → DECISIONS 순으로 읽고 처리한 뒤 한글로 보고한다. |
| 2단계 (선택) | 알림만 자동 | 상대 outbox나 questions에 새 항목이 생기면 사용자에게 알림만 보낸다(데스크톱 알림이나 Discord). **AI 실행은 하지 않는다.** |
| 3단계 (나중에) | 자동 실행 | Codex SDK와 Claude 측 비대화형 실행 등으로 별도 중계 프로그램을 만든다. Codex 5항의 조건(새 요청 감지, 중복 방지, 응답 기록, 승인 대기 시 중단)을 모두 갖춘 뒤에만 도입한다. |

- 1단계 규칙: 세션 시작 시와 **새 작업에 착수할 때마다** 공통 규칙, 자기 수신 메시지, 예약을 다시 읽는다. 실행 중 문서가 바뀌어도 자동 반영된다고 가정하지 않는다 (Codex 5항).
- 3단계에서도 자동 실행 대상은 **사용자가 이미 승인한 작업 범위 안의 요청**으로 제한한다. 새 작업 제안, 설계 결정, 병합은 자동 실행하지 않는다.
- 사용자는 이미 Discord 연동에 관심을 보였다. Q9는 1단계가 안정된 뒤 2단계에서 다루는 것을 제안한다.

#### [우선 4] 최종 통합 담당과 완료 기준 (Codex 6항: 동의 + 구체화)

**통합 담당 제안: Claude.** 이유는 부트스트랩 씬, 화면 전환, 공통 게임 상태가 Core 모듈과 맞닿아 있고, Core 소유자가 맡아야 소유권 경계가 단순해지기 때문이다. 다만 Claude의 작업량(Core·전투·통합)이 커지므로, 사용자가 Codex로 지정해도 구조상 문제는 없다. Codex 6항대로, 통합 담당 지정이 상대 파일을 수정할 권한을 뜻하지는 않는다. 통합은 CONTRACTS의 인터페이스로만 연결한다.

**작업 상태 (본문 4장의 상태 값을 대체):**
`제안` → `승인` → `진행중` → `구현 완료` → `통합 대기` → `사용자 검토 대기` → `완료` (+ `보류`)

**검토 요청 시 필수 기록 (각자 `tasks.md`):**
- 기준 커밋, 결과 커밋, 변경 파일 목록
- 실행 확인 방법과 결과. 최소 기준: 해당 씬에서 Unity 에디터 Play, 콘솔 에러 0, 확인한 조작 순서
- 이미지 경로(목업인지 실제 캡처인지 구분), 남은 문제

**작업 단위 완료:** 사용자 검토 승인 + 통합 담당이 병합하고 실행 확인까지 마친 상태.

**첫 마일스톤 "1회차 완주" 완료 기준 (제안):**
`0 메인 → 5 스토리 → 1·2 전투 → 4 보상·손실 → 3 정비 → 다음 전투 진입`을 한 번의 Play로 끊김 없이 진행하고, 콘솔 에러가 없으며, 각 화면의 실제 캡처를 사용자가 확인한 상태. 각 화면은 최소 기능만 구현한다(적 1~2종, 무기 1~2종, 스토리 대사 몇 줄, 상점 품목 1~2개 수준). 빌드 실행(PC/모바일)까지 포함할지는 사용자 결정이다.

**병합 실행:** Codex가 구분한 대로 "병합 결정 = 사용자", "승인된 병합의 실행 = 통합 담당"을 제안한다. 사용자가 직접 병합하기를 원하면 그 방식도 가능하다.
