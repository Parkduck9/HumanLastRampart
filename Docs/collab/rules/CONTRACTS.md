## C-002 어셈블리(asmdef) 구성과 의존 방향
- 상태: **승인** (2026-10-13, 사용자 확정 D-014. r3 기준 — C3 답변 포함)
- 위치: 각 모듈 폴더의 `.asmdef` 파일
- 정의:

  | 어셈블리 이름 | 폴더 | 기본 네임스페이스 | 소유 | 참조할 수 있는 것 |
  |---|---|---|---|---|
  | `HLR.Core` | `_Project/Core/` | `HumanLastRampart.Core` | Claude | (없음) |
  | `HLR.App` | `_Project/App/` | `HumanLastRampart.App` | Claude | Core |
  | `HLR.Combat` | `_Project/Combat/` | `HumanLastRampart.Combat` | Claude | Core |
  | `HLR.Frontend` | `_Project/Frontend/` | `HumanLastRampart.Frontend` | Codex | Core, UI |
  | `HLR.Story` | `_Project/Story/` | `HumanLastRampart.Story` | Codex | Core, UI |
  | `HLR.Story.Editor` | `_Project/Story/Editor/` | `HumanLastRampart.Story.Editor` | Codex | Core, Story (에디터 전용) |
  | `HLR.Meta` | `_Project/Meta/` | `HumanLastRampart.Meta` | Codex | Core, UI |
  | `HLR.UI` | `_Project/UI/` | `HumanLastRampart.UI` | Codex | Core |

  ```
  HLR.Core  ◀── App, Combat, UI
     ▲
     └── Frontend, Story, Meta ──▶ HLR.UI
                     Story ◀── Story.Editor
  ```
  - **금지:** 표에 없는 참조, 순환 참조. 특히 화면 모듈끼리(Combat↔Meta, Frontend↔Story 등) 직접 참조하지 않는다. App도 화면 모듈을 참조하지 않는다 (C-003의 인터페이스로만 연결).
  - **Unity 패키지 참조:** 각 어셈블리는 필요한 Unity 패키지 어셈블리(`Unity.InputSystem`, `Unity.TextMeshPro`, `UnityEngine.UI` 등)를 자유롭게 참조할 수 있다. 새 **패키지 설치**는 사용자 승인 (RULES 8장).
  - **ARCHITECTURE와 다른 점 (C3 답변: 허용):** ARCHITECTURE 3장 표에는 "모든 모듈은 Core만 참조"로 적었지만, Q-A1에서 공용 UI를 따로 두기로 했으므로 **Codex 화면 모듈(Frontend·Story·Meta)이 `HLR.UI`를 참조하는 것을 허용**한다(Codex 동의 M-CX-007). Combat은 전투 HUD를 자기 안에 두므로 UI를 참조하지 않는다. 승인되면 ARCHITECTURE 3장도 맞춘다.
  - 에디터 전용 코드는 `Editor/` 폴더와 별도 asmdef(Include Platforms: Editor)에 둔다.
  - 기본 어셈블리(`Assembly-CSharp`)에는 게임 코드를 두지 않는다. 템플릿 예제 코드는 C2 결정에 따른다.
- 사용처: 모든 모듈
- 변경 규칙: 참조 추가는 새 버전 + 사용자 승인. 순환이 생기는 변경은 승인하지 않는다.

## C-003 화면 전환
- 상태: **승인** (2026-10-13, 사용자 확정 D-014. r3 기준 — Codex 검토 M-CX-007 반영, C4 답변 포함). 단 `IScreenContext.Campaign`의 타입 `CampaignState` 내용은 C-004에서 정한다
- 위치: `HLR.Core` (`HumanLastRampart.Core.Flow`), 구현은 `HLR.App`
- 정의:

  **1) 기본 방식** — `Boot` 씬은 게임 내내 열려 있다. 화면 씬은 한 번에 하나만 추가로 열고(Additive), 다음 화면으로 갈 때 닫는다. 진행 데이터는 Boot(App)에 있어 화면을 바꿔도 사라지지 않는다.

  **2) Core에 둘 약속 (코드 형태 제안)**
  ```csharp
  namespace HumanLastRampart.Core.Flow
  {
      // 화면 목록. 씬 이름과 같다 (C-001).
      public enum ScreenId { MainMenu, Story, Battle, Result, Prep }

      // 화면이 끝날 때 App에 알리는 이유. 어디로 갈지는 App이 정한다 (Q-A3).
      public enum ScreenOutcome
      {
          Done,           // 이 화면의 일을 마침 (기본)
          StartNewGame,   // 메인: 시작
          QuitGame,       // 메인: 종료
          BackToMainMenu  // 어느 화면이든: 메인으로 돌아가기
      }

      // 각 화면 씬에 하나씩 두는 진입 컴포넌트가 구현한다 (화면 담당자 소유).
      public interface IScreenEntry
      {
          ScreenId Id { get; }
          void OnEnter(IScreenContext context);  // 씬이 열린 뒤 App이 한 번 호출
          void OnExit();                          // 씬을 닫기 직전 App이 한 번 호출
      }

      // App이 구현해서 화면에 넘겨준다.
      public interface IScreenContext
      {
          CampaignState Campaign { get; }         // 진행 데이터 (형태는 C-004에서 정함)
          void Complete(ScreenOutcome outcome);   // "끝났다" 신호. 한 화면에서 한 번만
      }
  }
  ```
  - 화면은 다른 화면 이름을 알지 않는다. `GoTo(다음 화면)` 같은 직접 이동은 두지 않는다.
  - 화면 데이터 전달(전투 시작 정보 `BattleSetup`, 전투 결과 `BattleResult`)은 `CampaignState` 안이나 C-005·C-006에서 정한다. C-003은 "열기·끝내기"만 정한다.

  **3) 진입 컴포넌트 규칙**
  - 각 화면 씬의 루트에 `IScreenEntry`를 구현한 컴포넌트를 **정확히 하나** 둔다. App은 씬을 연 뒤 이것을 찾아 `OnEnter`를 부른다.
  - 화면은 `OnEnter` 전에 진행 데이터를 읽거나 바꾸지 않는다.
  - `Complete`를 부른 뒤에는 그 화면에서 진행 데이터를 바꾸지 않고, 게임 입력도 처리하지 않는다 (App이 다음 화면으로 넘어가는 중).
  - `OnExit`에서 화면은 자기가 켠 입력 처리·코루틴·이벤트 구독을 정리한다.

  **3-1) App의 방어 규칙** (r2, M-CX-007 요청 1) — 화면 쪽 실수가 있어도 흐름이 꼬이지 않도록 App이 아래처럼 동작한다.
  - **화면마다 새 컨텍스트:** App은 화면을 열 때마다 `IScreenContext`를 새로 만들어 넘긴다. 이 컨텍스트는 그 화면의 `OnExit`가 끝나면 **무효**가 된다.
  - **무효 컨텍스트 호출:** 무효가 된 컨텍스트의 `Complete`는 무시하고 경고 로그를 남긴다(이전 화면의 늦은 콜백 차단). `Campaign`에 접근하면 `InvalidOperationException`을 던진다(개발 중 실수를 바로 찾기 위해).
  - **중복 `Complete`:** 한 컨텍스트에서 처음 받아들인 `Complete`만 처리하고, 이후 호출은 무시하고 경고 로그를 남긴다.
  - **허용되지 않은 신호:** 화면별로 받을 수 있는 신호가 정해져 있다(아래 표). 표에 없는 신호는 무시하고 에러 로그를 남긴다. 이 경우 받아들인 것으로 세지 않으므로 화면은 올바른 신호를 다시 보낼 수 있다.

    | 화면 | 받을 수 있는 신호 |
    |---|---|
    | MainMenu | StartNewGame, QuitGame |
    | Story, Battle, Result, Prep | Done, BackToMainMenu |

  - **`OnEnter` 안에서 바로 `Complete`:** 허용한다. App은 `OnEnter`가 끝난 뒤 전환을 시작한다.
  - **전환 순서:** `Complete` 받아들임 → 입력 차단 → 현재 화면 `OnExit` → 컨텍스트 무효화 → 현재 씬 닫기 → 다음 씬 열기 → 진입 컴포넌트 찾기 → 새 컨텍스트로 `OnEnter` → 입력 차단 해제.
  - **입력 차단:** 전환 중에는 App이 Boot의 `EventSystem`을 꺼서 UI 클릭을 막고, 화면을 덮는 전환용 화면(검은 화면 또는 페이드)을 Boot에 띄운다. 게임 입력은 위 3)의 화면 의무(`Complete` 뒤 입력 처리 안 함)로 막는다.

  **3-2) 씬에 두는 공용 오브젝트** (r2, M-CX-007 요청 2) — 씬을 겹쳐 열 때 같은 종류가 두 개 생기지 않도록 정한다.

  | 오브젝트 | 두는 곳 | 소유 | 수명 |
  |---|---|---|---|
  | `EventSystem` + `InputSystemUIInputModule` | **Boot에만 하나** | Claude | 게임 내내 |
  | 전환용 화면(페이드 Canvas) | Boot | Claude | 게임 내내 |
  | 카메라(`Camera`) | **각 화면 씬에 하나** | 그 씬 소유자 | 그 화면이 열린 동안 |
  | `AudioListener` | 각 화면 씬의 카메라에 하나 | 그 씬 소유자 | 그 화면이 열린 동안 |

  - 화면 씬에는 `EventSystem`을 두지 않는다. Boot에는 카메라와 `AudioListener`를 두지 않는다(화면 씬은 한 번에 하나만 열리므로 카메라·리스너도 항상 하나).
  - 전환 중 화면 씬이 없는 짧은 순간에는 Boot의 전환용 화면(카메라가 필요 없는 Overlay Canvas)만 보인다.
  - 화면 씬을 단독으로 테스트할 때 필요한 `EventSystem`은 5)의 테스트용 진입 방법이 대신 만든다.

  **3-3) 오류 처리** (r2, M-CX-007 요청 2)
  - **씬 열기 실패, 또는 진입 컴포넌트가 0개·2개 이상:** App은 에러 로그(씬 이름과 원인)를 남기고 그 화면의 `OnEnter`를 부르지 않는다. 그다음 MainMenu로 돌아간다. MainMenu 자체가 실패하면 더 이동하지 않고 에러 로그만 남긴다(무한 반복 방지).
  - 1회차에서는 오류 화면을 따로 만들지 않는다. 콘솔 에러로 확인한다.

  **4) 다음 화면 순서표 (App 한 곳에서 관리)** — 1회차 완주 기준 제안

  | 현재 화면 | 받은 신호 | 다음 |
  |---|---|---|
  | (게임 시작) | — | MainMenu |
  | MainMenu | StartNewGame | Story (새 진행 데이터 생성) |
  | MainMenu | QuitGame | 게임 종료 (에디터에서는 Play 중지) |
  | Story (일반 스토리) | Done | Battle |
  | Battle | Done | 승리: Result / **패배: Story (패배 엔딩)** |
  | Story (패배 엔딩) | Done | MainMenu (진행 데이터 폐기, 처음부터) |
  | Result | Done | Prep |
  | Prep | Done | Battle (다음 전투) |
  | 어느 화면이든 | BackToMainMenu | MainMenu |

  - **패배 흐름 (C4 답변):** 전투에서 지면 **4번 결과 화면을 건너뛰고** 바로 5번 스토리 화면에서 패배 엔딩(캐릭터 + 대사)을 보여 준 뒤 메인 화면으로 간다. 새 화면을 만들지 않고 스토리 화면을 다시 쓴다. 엔딩 내용은 Codex가 스토리 데이터로 만든다.
  - 이 분기를 위해 App은 두 가지를 알아야 한다. **(a) 전투 승패**, **(b) 스토리 화면이 지금 무엇을 재생할지(일반 스토리 / 패배 엔딩).** 화면 신호(`ScreenOutcome`)를 늘리지 않고, 이 값은 진행 데이터와 전투 결과 약속에서 정한다 → C-004 `CampaignState`, C-006 `BattleResult`, C-009 스토리 데이터에 반영할 요구사항.
  - 나중에 스토리를 전투 사이에 넣는 등의 변경은 이 표(App)만 고친다.

  **5) 단독 테스트** — 화면 씬 하나만 열고 Play해도 테스트할 수 있도록 Claude가 Phase 2에서 테스트용 진입 방법을 제공한다(ROADMAP P2-C06). 방식은 그때 제안한다.
- 사용처: App(Claude) 구현, 모든 화면(Claude·Codex)의 진입 컴포넌트
- 변경 규칙: `ScreenId`·`ScreenOutcome` 값 추가나 인터페이스 변경은 새 버전 + 사용자 승인. 순서표(4)의 변경도 사용자 승인. 값을 지우거나 이름을 바꾸지 않는다.

## C-004 진행 데이터 `CampaignState`
- 상태: **승인** (2026-10-13, 사용자 확정 D-015. r3 기준 — Codex 검토 M-CX-009 반영, D1·D2·D5 답변 포함). 단 `TrapPlacement`·`TargetingSettings`·`BattleResult`의 내용은 C-008·C-011·C-006에서 정한다
- 위치: `HLR.Core` (`HumanLastRampart.Core.Campaign`). 실제 객체는 App이 만들고 보관한다(C-003).
- 정의:

  **1) 원칙**
  - 한 판(새 게임 ~ 패배 엔딩)의 진행 상황은 **이 객체 하나**에 모은다. 화면끼리 값을 직접 넘기지 않는다.
  - **일반 C# 클래스**로 만든다. ScriptableObject에 진행 값을 쓰지 않는다 (RULES 9장 5번).
  - 정의 데이터(C-010)는 **ID 문자열로만** 가리킨다(에셋 직접 참조 금지). 나중에 저장 기능을 붙일 때 그대로 쓸 수 있게 하기 위해서다(Q-A7: 1회차는 저장 없음).
  - 메인 화면에서 "시작"하면 App이 새로 만들고, 패배 엔딩 뒤 메인으로 가면 버린다(D-014 C4).

  **2) 필드 (제안)**
  ```csharp
  namespace HumanLastRampart.Core.Campaign
  {
      public sealed class CampaignState
      {
          public int BattleNumber;                 // 다음(또는 진행 중) 전투가 몇 번째인지. 1부터
          public int Gold;                         // 화폐. 1회차는 골드 하나 (D2)

          public List<WallSegmentState> Wall;      // 성벽 구간별 상태 (구간 수는 전투 설계 P1-C09에서)
          public List<HeroState> Heroes;           // 주인공·특수 장교·강력한 병사: 한 명씩 관리
          public List<SquadState> Squads;          // 일반·특수 병사: 분대별 인원 수로 관리 (D1)
          public List<TrapPlacement> Traps;        // 설치한 함정 — 형태는 C-008에서 정함

          public TargetingSettings Targeting;      // 표적 우선순위 설정, 다음 전투에도 유지(Q-A5) — 형태는 C-011에서 정함

          public StoryRequest NextStory;           // 스토리 화면이 다음에 재생할 것 (D-014 C4)
          public BattleResult LastBattle;          // 가장 최근 전투 결과, 없으면 null — 형태는 C-006에서 정함

          public int NextInstanceNumber;           // 고유 ID 발급용 번호 (r2). 아래 NewInstanceId만 사용
          public string NewInstanceId(string prefix);  // 예: "squad_7", "hero_2", "trap_3". 이 판 안에서 겹치지 않음
      }

      public sealed class WallSegmentState { public string SegmentId; public int MaxHp; public int Hp; }

      public sealed class HeroState
      {
          public string InstanceId;   // 이 판에서의 고유 ID ("hero_" 접두사)
          public string UnitDefId;    // C-010 UnitDef
          public int Hp;
          public bool IsAlive;
          public string PostId;       // 배치 지점 (r2). 미배치면 null. 지점 목록은 전투 설계 P1-C09
          // 장착 아이템 등은 다음 마일스톤 (FirstRead: 아이템 강화)
      }

      public sealed class SquadState
      {
          public string SquadId;      // 분대 고유 ID ("squad_" 접두사, r2). 결과 반영은 이 ID로 맞춘다
          public string UnitDefId;    // C-010 UnitDef (병종). 같은 병종이 여러 분대일 수 있다
          public int Count;           // 인원 수. 0이 되면 반영하는 쪽이 목록에서 뺀다
          public string PostId;       // 배치 지점. 미배치면 null
      }

      public enum StoryKind { Normal, DefeatEnding }
      public sealed class StoryRequest { public StoryKind Kind; public string StoryId; }  // StoryId 형식은 C-009
  }
  ```
  - `List`는 `System.Collections.Generic`. 필드 이름과 형태는 Phase 2 구현 때 C# 관례(프로퍼티 등)로 다듬을 수 있지만, **담는 정보와 쓰는 쪽(아래 3)은 이 약속을 따른다.**

  **3) 누가 언제 바꾸는가** — 같은 값을 두 화면이 동시에 고치지 않도록 정한다.

  | 필드 | 만들기·바꾸는 쪽 | 시점 |
  |---|---|---|
  | 객체 전체 | App | MainMenu `StartNewGame` 때 새로 생성(초기값은 1회차 설정), 패배 엔딩 후 폐기 |
  | `BattleNumber` | App | 전투가 끝나 Result로 갈 때 1 증가 |
  | `NextStory` | App | 새 게임 시작 시 첫 스토리, 전투 패배 시 `DefeatEnding` |
  | `LastBattle` | App: Battle을 열기 직전 `null`로 비움 (r2) / Combat: 전투 종료 직전 한 번 기록 | 이전 결과를 다시 쓰는 일 방지 |
  | `Targeting` | Combat(Battle 화면) | 전투 중 플레이어가 바꿀 때 |
  | `Gold`, `Heroes`, `Squads`, `Wall` | Meta(Result·Prep 화면) | 결과 반영(C-007)과 정비(수리·모집·상점) |
  | `Heroes`·`Squads`의 `PostId` | App: 새 게임 때 `CampaignStartDef`의 첫 배치로 채움 / **Meta(Prep 화면)**: 정비 중 배치 변경 (D5) | Battle 화면은 배치를 바꾸지 않는다(가서 대포·표적 설정만) |
  | `Traps` | Meta: Prep(구매·배치) / **Result(전투에서 쓴 함정 반영, r2)** | 함정 구매·배치는 C-008, 소비 반영은 C-007 |
  | `NextInstanceNumber` | 새 분대·영웅·함정을 만드는 쪽 | `NewInstanceId` 호출로만 |
  | (읽기) | 모든 화면 | 자기 화면이 열려 있는 동안(C-003 컨텍스트 유효 기간) |

  - **전투 중 손실은 Combat이 `CampaignState`에 직접 쓰지 않는다.** 잃은 병력·성벽 피해·**발동해서 없어진 함정**은 `LastBattle`(C-006)에 담고, Result 화면이 한 번만 반영한다(C-007). 이렇게 하면 결과가 한 번만 반영된다 (r2, M-CX-009 요청 1).
  - **식별 (r2, M-CX-009 요청 2):** 결과의 손실은 병종 ID가 아니라 `SquadId`·영웅 `InstanceId`·함정 고유 ID(C-008)로 가리킨다. 같은 병종을 두 지점에 나눠도 어느 분대가 몇 명 잃었는지 정확히 맞출 수 있다.
  - **C-006·C-007에 넘길 요구사항 (r2):** `BattleResult`는 끝난 전투의 번호(`BattleNumber`)를 담는다. Result는 결과 번호가 현재 전투와 맞는지, 이미 반영했는지 확인한 뒤 한 번만 반영한다(중복 반영 방지 규칙은 C-007에서).
  - 패배 시에는 Result를 건너뛰므로 반영하지 않는다(어차피 폐기).
  - 전투 승패: App은 Battle의 `Done` 신호를 받으면 `LastBattle`의 승패 값을 보고 Result(승리) 또는 Story 패배 엔딩(패배)으로 보낸다(C-003 순서표).

  **4) 1회차 초기값** — 시작 골드, 시작 병력, 성벽 구간 수·내구도 같은 숫자는 이 약속에 적지 않는다. 정의 데이터의 "1회차 시작 설정" 에셋(C-010 `CampaignStartDef`)에서 읽는다.
- 사용처: App(생성·보관·흐름), Combat, Frontend(시작 신호만), Story(`NextStory` 읽기), Meta
- 변경 규칙: 필드 추가는 새 판(r)으로 기록하고 사용자 승인. 필드 삭제·의미 변경은 사용 중인 쪽의 동의(메시지) + 사용자 승인. 쓰는 쪽(3) 변경도 사용자 승인.

## C-010 정의 데이터 클래스
- 상태: **승인** (2026-10-13, 사용자 확정 D-015. r3 기준 — Codex 검토 M-CX-009 반영, D3·D4 답변 포함). 단 `TrapDef` 필드는 C-008, `ItemDef` 효과는 Codex 정비 설계(P1-X06)에서 정한다
- 위치: 클래스는 `HLR.Core` (`HumanLastRampart.Core.Definitions`), 에셋은 C-001의 `Data/` 하위 폴더
- 정의:

  **1) 공통 규칙**
  - 모두 **ScriptableObject**이고 공통 부모 `DefinitionBase`(`Id`, `DisplayName`)를 상속한다. 기본 수치만 담고, 게임 중에 값을 바꾸지 않는다(읽기 전용으로 쓴다).
  - 모든 정의는 고유 `Id`(영문 소문자·숫자·`_`, 예: `enemy_ghoul`)와 화면에 보일 `DisplayName`(한국어, Q-A6)을 가진다. 진행 데이터는 이 `Id`로 가리킨다(C-004).
  - **클래스(코드)는 Claude가 Core에 만들고, 에셋(실제 수치)은 C-001 폴더 소유자가 만든다.** 필드 추가는 Core 변경이므로 메시지로 요청한다.
  - 수치 밸런스는 약속이 아니다. 에셋 소유자가 자유롭게 고친다.

  **2) 클래스 목록 (제안)**

  | 클래스 | 에셋 위치·작성 | 담는 것 (1회차 최소) |
  |---|---|---|
  | `UnitDef` | `Data/Combat/` Claude | 아군 유닛: 구분(`UnitKind`: Hero 주인공 / Officer 특수 장교 / Elite 강력한 병사 / Soldier 일반 병사 / SpecialSoldier 특수 병사), 최대 체력, 기본 무기(`WeaponDef` ID), 모집 비용, 스프라이트 |
  | `WeaponDef` | `Data/Combat/` Claude | 무기: 종류(`WeaponKind`: Bow 활 / Crossbow 석궁 / Cannon 대포 / Gun 총 / Magic 마법 …), 피해, 사거리, 공격 간격, 범위(광역이면 반경) |
  | `EnemyDef` | `Data/Combat/` Claude | 적: 일반/특수 구분(`IsSpecial`), 최대 체력, 이동 속도, 성벽 공격력, 처치 보상 골드, 스프라이트 |
  | `WaveDef` | `Data/Combat/` Claude | 전투 하나의 적 구성: 등장 순서·수·간격 (상세는 전투 설계 P1-C09) |
  | `TrapDef` | `Data/Traps/` 공용 | 함정: 가격, 발동 조건, 피해 — **필드와 작성자 경계는 C-008에서 정함** |
  | `ItemDef` | `Data/Meta/` Codex | 상점 품목: 가격, 효과 종류 — 1회차 품목과 효과는 Codex 정비 화면 설계(P1-X06)에서 정함 |
  | `CampaignStartDef` | `Data/Combat/` Claude (D3) | 1회차 시작 설정: 시작 골드, 시작 영웅·분대와 **첫 배치 지점**(D5), 성벽 구간과 내구도, 첫 스토리 ID, 전투 번호별 `WaveDef`. Codex는 정비 쪽 값 조정이 필요하면 메시지로 요청 |

  - 종류 목록(`UnitKind`, `WeaponKind`)은 FirstRead의 병력·무기 구분을 따른다. 1회차에 실제로 쓰는 것은 일부(무기 1~2종, 적 1~2종 — RULES 12장)이고, 나머지 값은 미리 두기만 한다.
  - `StoryDef`(스토리 데이터)는 C-009에서 Codex 제안으로 정한다. 상점 외 모집 목록·수리 비용 정의가 필요하면 Codex가 P1-X06 설계에서 제안한다.

  **3) 정의 찾기**
  ```csharp
  namespace HumanLastRampart.Core.Definitions
  {
      public interface IDefinitionLookup
      {
          T Get<T>(string id) where T : DefinitionBase;   // 없으면 null + 에러 로그
          IReadOnlyList<T> All<T>() where T : DefinitionBase;
      }
  }
  ```
  - App이 구현해서 화면에 넘긴다. `IScreenContext.Definitions`로 받는다 (D4, C-003 v1.1).
  - 에셋 목록은 소유자별 **카탈로그 에셋**으로 모은다: `Data/Combat/CombatCatalog`(Claude), `Data/Meta/MetaCatalog`(Codex), `Data/Story/StoryCatalog`(Codex), `Data/Traps/TrapCatalog`(C-008에서 작성자 결정). 각 소유자가 자기 카탈로그에 에셋을 등록하고, Claude가 Boot에서 카탈로그들을 연결한다.

## C-005 전투 준비 정보 BattleSetup
- 상태: **제안 r1**
- 위치 제안: HLR.Core / HumanLastRampart.Core.CombatContracts (클래스 구현 담당 Claude, 이번에는 문서만 작성).

### 전달할 정보
| 항목 | 의미 |
|---|---|
| BattleRunId | 이번 전투 실행의 고유 문자열 ID. App이 매번 새로 발급하며 새 게임에서도 이전 실행과 겹치지 않음 |

| Wall | SegmentId·MaxHp·Hp의 복사본 |
| Traps | 고유 배치 ID를 보존한 설치 함정 복사본. 상세 필드는 C-008에서 확정 |

- ID 중복, 누락된 정의/웨이브, Hp 범위, 음수 분대 수, 없는 배치 지점은 시작 전 검증한다. 지점 규격은 전투 설계에서 확정한다. 0명 분대·사망 영웅·미배치 병력의 실제 참가 규칙은 전투 설계에서 정하며 임의로 전장에 넣지 않는다.

- 웨이브가 없는 다음 전투 번호의 완료/엔딩 정책은 결정 필요 E3. 마지막 웨이브 자동 반복은 하지 않는다.

## C-006 전투 결과 BattleResult
- 상태: **제안 r1**
- 위치 제안: HLR.Core / HumanLastRampart.Core.CombatContracts.
- 만드는 쪽: Combat. 읽는 쪽: App(승패 분기), Meta.Result(승리 결과 표시·반영), Story(패배 엔딩 재생; 전투 데이터 상세 사용은 C-009에서 정함).

### 전달할 정보
| 항목 | 의미 |
|---|---|
| BattleRunId | 시작 BattleSetup과 같은 실행 ID |
| BattleNumber | **끝난 전투 번호**. 다음 번호로 바뀐 Campaign.BattleNumber를 복사하지 않음 |
| Outcome | Victory 또는 Defeat. 판정 조건은 전투 설계에서 정함 |
| DefeatedEnemyCount | 처치 수. 0 이상 |
| EarnedGold | 얻은 골드. 0 이상. 승리 시만 반영 |
| HeroOutcomes | InstanceId별 HpAfter·IsAliveAfter. 참가 영웅 각각 정확히 한 항목 |
| SquadLosses | SquadId별 LostCount. 시작 Count 이하, 0 이상. 손실 있는 분대만 기록 가능 |
| WallOutcomes | SegmentId별 HpAfter. 시작 Hp 이하, 0 이상. 피해 있는 구간만 기록 가능 |
| ConsumedTrapIds | **발동해 소비된** 함정의 고유 배치 ID 목록. 함정 정의 ID와 다름 |

- BattleSetup의 영웅/분대/성벽/함정 ID로 결과를 식별한다. 같은 병종을 여러 지점에 배치해도 SquadId로 손실 대상을 정확히 맞춘다.
- 목록은 null이 아닌 빈 목록을 허용한다. 동일 ID의 중복 항목, 알 수 없는 ID, 잘못된 범위는 유효한 결과로 받지 않는다. 병종 ID로 대신 매칭하거나 중복을 합쳐 숨기지 않는다.
- 영웅의 사망은 HpAfter=0, IsAliveAfter=false와 일치해야 한다. 부활·전투 중 회복/모집·수리는 현재 초안에 포함하지 않으며 추가 시 결과 규격을 다시 검토한다.
- 소비되지 않는 함정의 반복 발동 횟수와 재사용 여부는 C-008에서 정한다. ConsumedTrapIds에 있는 설치물만 제거하고 모든 발동 함정을 임의로 삭제하지 않는다.
- Combat은 전투 종료 시 결과를 한 번 완성하고 Campaign.LastBattle에 기록한 뒤 Complete(Done)를 보낸다. 이후 결과를 수정하지 않는다.
- App은 실행 ID와 끝난 번호, 승패와 결과 형식을 먼저 검사한다. null/이전 실행/잘못된 결과이면 승리·패배 분기를 진행하지 않고 에러를 기록해 메인으로 복귀한다.
- **승리:** C-004에 따라 App이 Campaign.BattleNumber를 끝난 번호+1로 한 번 증가시키고 Result를 연다.
- **패배:** 전투 번호를 증가시키지 않고 StoryRequest.Kind=DefeatEnding으로 패배 엔딩을 연다. Result를 건너뛰며 보상·손실·함정 소비를 Campaign에 반영하지 않는다(D-014). 엔딩 종료 후 Campaign을 폐기한다.

## C-007 결과 반영 규칙
- 상태: **제안 r1**
- 담당: Meta.Result(Codex). App은 흐름과 전투 번호만 관리한다. Combat은 결과만 만든다.

### 반영 시점과 중복 방지
- Result.OnEnter에서 승리 결과를 검사하고 **표시 전에 한 번** 반영한다(E1 제안). 다음 버튼은 반영을 다시 실행하지 않고 Complete(Done)만 보낸다.
- 반영 대상: 골드, 영웅 체력·생존, 분대 인원, 성벽 체력, 소비된 함정.
- 현재 ActiveBattleSetup과 LastBattle의 BattleRunId·BattleNumber가 모두 같아야 한다.
- 승리 Result에서 Campaign.BattleNumber는 LastBattle.BattleNumber+1이어야 한다. 현재 번호와 결과 번호가 같아야 한다고 검사하면 승인 C-004의 전투 번호 증가 시점과 충돌하므로 **끝난 번호+1**로 검사한다.
- LastAppliedBattleRunId가 같은 결과의 실행 ID이면 **이미 반영됨**으로 처리해 아무 값도 다시 변경하지 않는다. 화면에는 보관된 결과를 표시할 수 있다.
- 중복 여부 검사는 시작 상태와 현재 상태 비교보다 먼저 수행한다. 이미 반영됐으면 상태가 달라진 것이 정상이며 다시 검증·반영하지 않는다.
- App이 새 게임을 만들 때 반영 표시는 비운다. 전투마다 새로운 실행 ID로 다른 게임의 1번 전투 결과가 섞이지 않게 한다.
- LastBattle/ActiveBattleSetup은 Result 화면과 이후 Prep에서 반영 검사·표시를 마칠 때까지 보존하고, 다음 Battle 시작 때 새 준비 정보를 설정하며 LastBattle을 비운다.

### 모든 값 검증 → 새 상태 준비 → 한 번에 반영
1. 실행 ID·번호·Victory 여부·중복 여부 검사.
2. 모든 영웅/분대/성벽/함정 ID와 수치 범위를 시작 스냅샷 및 현재 Campaign과 대조. 결과 반영 전 Campaign의 해당 상태가 시작 상태와 다르면 잘못된 재반영/예상 밖 변경으로 거부한다.
3. 정비 이전의 새 리스트와 최종 골드를 메모리에서 준비한다. Gold+EarnedGold 정수 범위 초과도 먼저 검사한다. 이 단계에서는 Campaign을 수정하지 않는다.
4. 검증·준비가 모두 성공하면 동기 처리 한 구간에서 준비된 값들을 Campaign에 설정하고 **마지막에** LastAppliedBattleRunId를 기록한다. 중간에 기다리거나 화면 전환·외부 콜백을 호출하지 않는다.
5. 실패하면 준비한 값을 폐기한다. Campaign의 골드·병력·성벽·함정·반영 표시는 그대로 두고, 다음 버튼을 비활성화해 정비 진입을 막는다. 오류 로그 후 메인 복귀만 허용하는 것을 제안한다(E2).

### 반영 내용
- 골드: 현재 Gold + EarnedGold.
- 영웅: 참가 영웅별 Hp·IsAlive만 갱신. InstanceId·UnitDefId·PostId는 유지. 사망 영웅은 표시를 위해 목록에 남긴다; 이후 회복/퇴장 정책은 정비 설계에서 결정한다.
- 분대: 시작 Count에서 LostCount를 뺀다. 0명 분대는 승인 C-004대로 목록에서 제거한다. 살아남은 분대의 SquadId·UnitDefId·PostId는 유지한다.
- 성벽: 결과가 보고한 구간의 Hp를 HpAfter로 갱신. MaxHp·SegmentId는 유지한다.
- 함정: ConsumedTrapIds와 일치하는 설치물만 목록에서 제거한다. 소비되지 않은 설치물의 위치·정의는 유지한다. 전투 결과가 Prep의 구매 비용을 다시 청구하지 않는다.
- 표적 설정: Combat이 갱신한 값 유지. Result가 시작 스냅샷 값으로 되돌리지 않는다.
- 실패 엔딩: Result를 열지 않으므로 이 반영 절차를 실행하지 않는다.

- 지점별 설정이 있으면 그것을 사용하고, 없으면 DefaultPriority를 사용한다. F4 제안 기본값은 LowestHpRatio.
- 설정은 **성벽 배치 지점(PostId) 기준**으로 유지한다(F4). 정비 때 다른 병력을 그 지점에 배치해도 설정이 남는다. 분대 ID와 혼동하지 않는다.
- Combat이 플레이어의 설정 변경을 즉시 Campaign.Targeting과 전투 내부 설정에 기록한다(승인 C-004). Result는 덮어쓰지 않고 Prep은 읽기만 한다. 새 게임을 시작하면 초기값으로 돌아간다.
- 같은 PostId의 분대·영웅이 설정을 공유하는지와 지점별 수용 인원은 배치/전투 설계에서 정한다. TargetingSettings에는 병력의 이동/배치를 기록하지 않는다.

### 후보 선택과 동률 처리 (제안)
1. 살아 있으며 해당 공격이 실제로 맞힐 수 있는 **사거리/공격 조건 안의 적만** 후보로 만든다. 범위 밖 특수 적을 따라 공격을 멈추지 않는다.
2. LowestHpRatio: Hp/MaxHp가 가장 낮은 적. HighestHpRatio: 가장 높은 적. MaxHp는 0보다 커야 한다.
3. SpecialFirst: 후보 중 특수 적이 있으면 특수 적만 남긴 뒤 Hp/MaxHp 낮은 순. 없으면 전체 후보의 Hp/MaxHp 낮은 순.
4. 비율 동률이면 공격자와 가까운 적, 거리도 같으면 전투 내부의 고유 EnemyInstanceId 순으로 정한다. 같은 데이터에 항상 같은 결과가 나오게 한다.
5. 후보가 없으면 발사하지 않고 다음 판단 시점까지 대기한다. 이미 죽거나 범위 밖이 된 표적은 다시 선택한다. 판단 주기는 전투 설계에서 정한다.
- 고정 지점 포대/병사의 일반 자동 공격에 적용한다. 2번 지도에서 사용자가 찍는 특수 공격 위치, 함정의 자동 감지에는 이 설정을 적용하지 않는다.
- 투사체 발사 뒤의 명중·추적·광역 피해 판정은 무기/전투 설계의 별도 규칙이다. 지금은 발사 대상 선정만 정한다.

## C-008 r2 사용자 요구 반영 — 함정 회수·경로 위험·지형 변경
- 상태: **요구사항 기록 / 세부 설계 제안**, 2026-10-13 T-CX-007. 사용자 F1·F2 변경 지시를 보존한다. 지형 변경 방식·회수 실행 방식 답변 전까지 데이터/API 최종 승인으로 보지 않는다.
- 대체 대상: C-008 r1의 '미발동 함정 자동 다음 전투 유지', '한 전장·고정 설치 지점만 사용', '적에게만 피해', '함정 재고 보관 제외' 가정. 해당 r1은 과거 제안으로 보존하며 새 설계에서는 아래 요구를 우선한다.

### 사용자 요구 (확정 방향)
1. 전투 중 함정은 적 접근 시 자동 발동하는 일회용이다.
2. 승리 후 미발동 함정은 **회수를 선택할 수 있고, 회수하지 않는 선택도 있다.** 미발동 설치물을 자동으로 회수하거나 삭제하지 않는다.
3. 지도에 정확한 위치를 체크하지 않았다면 회수하지 못할 수 있다. 실제 함정 위치와 플레이어가 지도에 기록한 위치/정보는 별도로 보관한다.
4. 성에서 회수 경로를 지정한다. 회수 병력이 근처에서 확인한 함정은 체크해서 회수할 수 있으나, 확인하지 못한 함정이 이동 경로에 있으면 폭발해 추가 병력 손실이 생길 수 있다.
5. 승리 후 충원·용병 영입 등의 정비 구간에서 지형을 바꿀 수 있고, 바뀐 지형에서 함정을 설치할 수 있어야 한다. 지형 변경 방식은 사용자 질문 답변 후 확정한다.
6. F3의 정비 중 이동·판매/환불 제한은 사용자 '제안대로 이어서' 방향을 따른다. 다만 F1의 회수 아이템 보관은 새 요구이므로 r1의 '재고 제외'에 우선한다. 매설된 함정을 현장 회수 없이 순간 이동하는 방식은 새 회수 위험과 충돌하므로 적용하지 않는다.

### 세부 설계에 필요한 상태 (후속 제안)
| 구분 | 정보 | 목적 |
|---|---|---|
| 전장 실제 설치 상태 | 설치 고유 ID·종류·지형/전장 ID·실제 위치·미발동/소비/회수 | 실제 위험과 결과 계산. 플레이어 지도에 전부 자동 노출하지 않음 |
| 지도 기록 | 표시 ID·전장 ID·기록 위치·정확도/확인 상태 | 미기록·부정확한 기록 때문에 회수 실패가 생길 수 있도록 실제 위치와 분리 |
| 회수 계획 | 회수 작업 고유 ID·투입 병력 고유 ID·이동 경로·수거 목표·회수 안 함 선택 | 경로·위험·실행 단위 관리 |
| 회수 결과 | 작업 ID·회수한 설치 ID·폭발해 소비된 설치 ID·추가 병력 손실·새로 확인한 지도 기록 | 승리 결과와 별도 작업으로 중복 없이 적용 |
| 회수 아이템 보관 | 함정 종류별 수량 또는 개별 아이템 ID | 회수된 함정을 다시 설치할 때 구매 비용을 재청구하지 않음 |
| 지형 상태 | 선택/편집 전장 정보 및 설치·통행 가능한 영역 | 지도 표시·회수 이동·다음 BattleSetup이 같은 지형을 사용 |

- 회수 성공은 설치물 제거와 회수 아이템 증가를 함께 처리한다. 회수 중 폭발한 함정은 제거하되 아이템으로 지급하지 않고 회수 결과의 병력 손실을 함께 적용한다. 반복 실행으로 아이템이 늘거나 병력이 다시 차감되지 않게 작업 ID로 1회 반영한다.
- 회수를 안 하면 지형에 남은 함정의 위험 상태를 보존한다. 지형을 바꿨다는 이유만으로 이전 함정·위험 정보를 지우지 않는다. 같은 장소의 지형 편집인지 다른 전장 선택인지에 따른 처리 경계는 답변 후 정한다.
- 기존 C-007은 **전투 결과**의 1회 반영 약속이다. 회수 손실을 기존 LastBattle에 끼워 넣거나 전투 결과를 다시 적용하지 않는다. 별도 회수 작업 결과와 새 반영 약속을 제안해 승인받는다.
- 기존 C-004·C-005·C-010에는 지도 기록·회수 계획/아이템·지형 변경 정보가 없다. 승인 본문은 바꾸지 않고 후속 버전 제안으로 연결해야 한다.
- 구매·재설치 UI/진행 반영은 Codex Prep, 전투·회수 중 경로 이동/감지/폭발 판정의 담당 경계는 후속 설계에서 명시한다. 대체 지시만으로 Claude Game 파일을 수정하지 않는다.

## C-008 r3 함정 이동으로 지도 정보가 오래되는 회수 위험
- 상태: **사용자 요구 방향 확정 / 세부 데이터·수치 제안** (2026-10-13, T-CX-007).
- 사용자 근거: '실시간 전투는 제외', 설치 때 지도 표시 가능, 격렬한 전투로 낮은 확률에 함정이 가까운 곳으로 이동해 회수 경로에서 터질 수 있다는 설정.
- 대체 대상: 바로 위 성 내부 실시간 전투 '미정' 메모의 범위 상태. 현재 범위에서는 **성 내부 실시간 전투 제외**로 기록한다. 성벽 전투와 회수 경로 위험은 유지한다.

### 설치·전투·회수 흐름
1. 설치할 때 플레이어가 지도에 위치 표시를 남길 수 있다. 표시하지 않고 설치하는 선택도 유지한다. 지도 기록과 실제 함정 상태는 별개다.
2. 격렬한 전투의 영향으로 **아직 발동하지 않은 설치물**이 작은 확률로 원래 위치 가까운 유효한 지면으로 이동할 수 있다. 소비·폭발한 함정은 이동하거나 회수 아이템으로 되살리지 않는다.
3. 실제 위치만 바뀌고, 설치 때 기록한 지도 표시가 자동으로 새 위치를 알려 주지는 않는다. 지도 위치를 정확히 표시했어도 전투 뒤에는 오래된 정보가 될 수 있다.
4. 회수는 그 시점의 **실제 위치**를 기준으로 탐지·접근·경로 충돌을 판단한다. 낡은 표시만 보고 이동하다 실제 함정의 발동 영역을 통과하면 폭발과 추가 병력 손실이 발생할 수 있다.
5. 병력이 근처에서 새 위치를 확인하면 지도 기록을 갱신하고 해당 함정을 회수할 수 있다. 아직 감지하지 못했으면 경로상의 위험이 남는다. 탐지/발동/해체의 우선순위와 반경은 별도 세부 설계에서 검토한다.
6. 회수하지 않는 선택도 남긴다. 남겨둔 함정의 실제 위치·소비 상태와 낡은 지도 표시를 보존한다.

### 정합성과 후속 데이터 연결 제안
- 설치물은 TrapId를 그대로 유지한다. '위치가 바뀐 함정'은 새 아이템이 아니다.
- r1의 SlotId 단독 위치는 이동을 표현할 수 없다. 실제 상태에는 전장/지형 ID와 실제 지면 좌표를 보관하고, 설치 슬롯이 남더라도 최초 설치 출처 정보로만 사용한다. 정확한 클래스/좌표 규격은 후속 버전에서 승인한다.
- 이동 목적지는 설치물/전장 경계·통행/회수 가능한 지면·성벽 충돌 등을 검증한다. 적합한 가까운 위치를 정할 수 없다면 원래 위치를 유지하는 것을 제안한다. 이동으로 접근 불가능한 공간에 들어가 자동 회수 불능이 되는 정책은 만들지 않는다.
- 확률 판정과 목적지는 전투 처리에서 확정해 결과에 저장한다. 결과 화면 재진입·회수 경로 수정·미리보기 때마다 다시 무작위로 뽑지 않는다. 난수 처리 횟수·전투 강도 조건·이동 범위는 미정이다.
- 후속 **C-006 v1.1 제안**: BattleResult에 surviving trap의 TrapId·이전 위치·전투 종료 후 실제 위치를 담는 위치 변경 결과를 추가한다. ConsumedTrapIds와 중복되는 설치물이면 잘못된 결과로 거부한다.
- 후속 **C-007 v1.1 제안**: 승리 결과 1회 반영 구간에서 소비 설치물을 제거하고, 살아남은 설치물의 새 실제 위치를 함께 적용한다. 지도 기록은 자동 수정하지 않는다. 오류 시 다른 결과와 함께 미반영 후 E2 안내를 따른다.
- 실제 위치 변경은 전투 결과, 회수 아이템/병력 손실은 회수 작업 결과로 분리한다. LastBattle을 회수 때 다시 적용하지 않고, 각각 고유 실행/작업 ID로 한 번만 반영한다.
- 확률·최대 이동 거리·탐지 거리·발동 반경·회수 인원/손실 수치는 사용자 검토 전까지 미정이다. '작은 확률'을 임의로 특정 퍼센트로 확정하지 않는다.
- 이 문서는 요구 방향과 연결 제안만 기록한다. 관련 C-004·005·006·007·010 실제 타입 변경은 연결안을 정리해 승인받은 후 구현한다.

### 범위와 남은 사항
- 성 내부 실시간 전투 제외는 확정한다. 함정 회수 장면에 병력 이동을 시각화할지, 경로 결과만 계산할지는 별개의 표현 선택이며 아직 특정되지 않았다.
- 지형 변경 R1(구성 선택/직접 편집), 회수 표현 R2, 일반 자동 공격 표적 F4는 기존 대기 상태를 유지한다.
- C-008의 회수/위치 이동 연결 설계는 진행 중, C-009 스토리 연계는 별도 대기. Game 구현 및 Unity 확인 없음.

## C-008 r4 지형 사이클·제한 편집·동시 회수·접이식 보고서
- 상태: **사용자 요구 방향 확정 / 연결 API·수치 제안** (2026-10-13, T-CX-007).
- 근거: 사용자 지형 4종·4전투=1사이클, 병력 투입으로 길 폭/굴곡 제한 편집, 원형 병력 얼굴 지도 이동, 동시 추가 파견, 지도 폭발, 오른쪽 보고서 펼침/접힘, 안전 귀환 시 낮은 확률 아이템 또는 돈.
- 대체 대상: R1·R2 미답변 상태, C-008 r1 단일 고정 전장 가정, E3 최소 두 전투 예시. 현재 사이클 설계에서는 **4개 지형 구성·4번 전투를 1사이클**로 둔다. 4번째 승리 즉시 메인 복귀로 고정하지 않는다. 다음 사이클 연결은 후속 설계에서 결정한다.

### 지형
- 기본 지형 4개를 준비한다. 각 지형의 형태와 4전투 순서는 사용자 화면/전투 설계에서 확정한다.
- 정비 중 병력을 투입해 기본 지형의 일부를 편집할 수 있다. 예: 통로를 좁히거나 구불구불하게 변경. 전장을 통째로 바꾸는 자유 맵 제작은 제외한다.
- 제안 상태: TerrainId·기본 지형 버전·허용 편집 영역·편집 작업 기록·투입 병력·완료 여부를 보관하고, 지도와 다음 BattleSetup은 같은 완료된 지형 상태를 사용한다.
- 허용 영역/변경량·병력 소요량·작업 시간은 미정이다. 성벽/진입 경로를 완전히 봉쇄하거나 설치물이 지면 밖으로 사라지는 편집을 막는 검증을 제안한다.
- 회수 경로가 이미 실행 중이면 그 경로 아래의 지형을 편집해 판정을 바꾸지 않도록, 영향 영역 편집을 대기시키는 정책을 제안한다. 전체 편집 잠금인지 영역별 대기인지는 UI/경로 설계에서 정한다.
- 미회수 함정은 원래 TerrainId와 실제 위치에 남는다. 현재 표시 지형을 바꿔도 제거하거나 다른 지형으로 옮기지 않는다. 다시 그 지형을 쓰면 같은 위험 상태를 참조한다.

### 회수 파견과 표시
- 병력 얼굴을 넣은 **원형 아이콘**이 지도 경로를 따라 이동한다. 이동은 시각화하지만 성 내부 실시간 전투는 제외한다.
- 부대 하나가 이동 중이어도 다른 가용 병력을 별도 경로로 파견할 수 있다. 각 작업은 자기 MissionId·TerrainId·투입 병력·경로·상태를 가진다.
- 제안 상태 순서: 계획 → 출발 → 이동/탐색 → 회수/폭발 사건 → 귀환 → 보고 완료. 중도 손실 후 계속할지 즉시 복귀할지, 전멸 기준은 미정이다.
- 출발한 병력은 귀환/종료까지 예약한다. 같은 병력을 다른 회수나 지형 작업에 중복 배정하지 않는다. 분대 일부 파견 시 Count 전체 대신 예약 인원과 가용 인원을 분리한다(후속 C-004 변경 제안).
- 경로와 실제 함정 위치/발동 반경을 비교한다. 설치 시 지도 표시는 자동 갱신하지 않고, 탐색으로 확인했을 때만 기록을 갱신한다.
- 폭발 시 **현재 지도 위치에서 폭발 효과**와 병력 손실 표시를 보여주고 즉시 보고서를 생성한다. 실제 손실/소비 상태는 사건 ID로 한 번만 반영한다.
- 여러 부대가 같은 설치물을 만나도 회수 또는 소비 상태 전이를 먼저 확보한 한 사건만 성공한다. 두 부대에 같은 함정 아이템을 지급하거나 같은 함정으로 여러 번 피해를 주지 않는다.
- 회수하지 않음 선택은 유지한다. 완료되지 않은 파견을 남긴 채 다음 전투를 시작할 수 있는지는 후속 상태 전환 설계에서 결정한다(안전한 기본 제안: 진행 중 작업이 끝나거나 복귀한 뒤 시작).

### 오른쪽 보고서
- 지도 오른쪽에 사건 보고서를 시간 순서로 쌓는다. 제목을 클릭하면 본문이 열리고 다시 클릭하면 접힌다. 지도/다른 파견은 보고서 확인 중에도 진행된다.
- 폭발·회수 성공·귀환 완료 등의 사건 시점에 보고서를 만든다. 모든 결과가 끝날 때까지 기다리지 않는다.
- 보고서 최소 정보: ReportId·MissionId·사건 시각·TerrainId/확인 위치·투입/귀환/손실 병력·회수 함정·추가 획득물. 보고서 확인은 읽기 상태만 바꾸고 보상 판정/지급을 다시 하지 않는다.
- 지도와 보고서의 연출은 동일한 실제 사건 기록을 사용한다. 보고서 속 위치 공개 범위는 탐색으로 확인한 정보까지만 둔다.

### 안전 귀환 추가 획득
- **성공적으로 돌아온 부대**는 낮은 확률로 아이템 또는 돈을 추가로 획득할 수 있다. 함정 회수 아이템과 별개의 보너스다.
- 귀환 완료 때 작업 ID 기준으로 판정·결과를 저장하고 한 번만 지급한다. 보고서를 열거나 접을 때, 페이지/화면을 다시 볼 때 재추첨·재지급하지 않는다.
- 확률·금액·아이템 목록·한 작업에서 돈/아이템 동시 지급 여부는 미정이다. 실제 게임 수치를 임의로 확정하지 않는다.
- 지도 표시용 돈 명칭은 승인 화폐 골드를 사용한다. 보너스 아이템 목록·정의 ID는 정비/상점 설계와 C-010 연결에서 제안한다.

### 담당·연결 작업
- 정비 지도·파견 UI·원형 아이콘·보고서·회수/보상 진행 데이터 반영은 Codex 설계 영역이다. 경로/지형/폭발 규칙의 구현 담당 경계는 합의된 계약에 명시한다. Claude 게임 파일 수정 허가는 아직 없다.
- 후속 C-004: 지형별 설치/지도 상태·작업/병력 예약·회수 재고·보고서·보너스 반영 ID. C-005: 해당 지형의 완료 편집 상태 스냅샷. C-006·007: 전투 종료 함정 실제 위치 결과. C-010: 지형/아이템/함정 정의. 승인 본문을 직접 덮어쓰지 않고 새 버전으로 연결한다.
- R1은 '정해진 4개 지형에서 제한 편집', R2는 '원형 병력 얼굴 실제 지도 이동 + 병렬 파견'으로 답변 완료다. F4 기본값·플레이어 변경 답변도 유지한다.
- 목업은 인터랙션 검토용이다. 임의 연출 시간·폭발·보너스 사건은 사례일 뿐 실제 확률·경로/전투 구현이 아니다.

## C-012 대량 적 데이터 처리·성능 검증 (제안 r1)
- 사용자 요구 확정 방향: 보유 에셋 최대 활용, 많은 적을 데이터 관리 방식으로 최적화. 우선 **동시에 살아 움직이고 공격하는 적 1,000마리**를 목표로 한다. 단순 누적 생성 수와 구분한다.
- 상태: 성능 목표 기록 / 구현 구조와 측정 합격선 제안. 1,000마리 무지연 달성이나 Game 구현 완료로 기록하지 않는다.
- 기존 ARCHITECTURE의 소수 적 완주 출발 계획은 최소 기능 연결용으로만 남긴다. 프로젝트 핵심 목적은 대량 적이 실제로 동작하는 상태의 성능이며 **초기 기반 단계에 성능 시험을 추가**한다. 적 종류 1~2종과 적 개체 수 1,000은 별개다.

### 구현 구조 후보
- ScriptableObject EnemyDef는 종류별 정의만 보관한다. 개별 적의 위치·체력·진행 상태는 연속된 런타임 데이터 저장소와 고유 적 ID로 관리하는 것을 제안한다.
- 데이터 갱신과 화면 표시를 분리하고, 개별 적마다 Update·Animator·복잡한 물리 판정을 기본 구성으로 붙이는 설계 대신 일괄 갱신/스프라이트 프레임 재생/필요한 충돌 판정을 비교한다.
- 공간 격자 등의 근접 후보 검색으로 모든 적을 매 공격마다 전부 비교하지 않는 방향을 검토한다. 피해·함정 광역 판정에서도 같은 후보 집합을 사용할 수 있다.
- 경로는 같은 목적지를 향한 공유 경로/흐름장 후보를 비교한다. 제한적 지형 편집 완료 시 TerrainVersion에 맞춰 경로/통행 정보를 갱신한다. 편집 때마다 모든 적의 개별 경로를 매 프레임 계산하는 방식은 피하는 것을 제안한다.
- 생성/제거와 표시 자원은 재사용하고, 다수 사망·웨이브 생성 구간의 할당/스파이크를 함께 검증한다. 적 ID 재사용 시 이전 투사체/표적 참조가 새 적에 적용되지 않는 세대/유효성 규칙을 둔다.
- CPU 데이터 처리와 GPU 표시를 각각 측정한다. 스프라이트 아틀라스·공유 머티리얼·배칭/인스턴싱 후보는 실제 에셋과 URP에서 검증 후 선택한다. 화면 밖 컬링으로 렌더링을 줄여도 적의 이동·공격 시뮬레이션 수를 부풀리지 않는다.
- ECS/DOTS는 후보이지 사용자 확정이 아니다. 기존 데이터 배열 기반 + Jobs/Burst 방식과 Entities 방식의 작업량·에셋 호환·유지보수·실측 성능을 비교한 뒤 구조를 승인받는다.

### 조기 측정과 합격선 제안
- 측정 규모: 100·500·1,000 동시 활성. 1,000을 통과하면 더 높은 수의 상한을 추가 측정할 수 있다. 5,000/10,000을 현재 사용자 목표로 기록하지 않는다.
- 적 이동·공격·피해/죽음·함정 폭발·스프라이트 애니메이션·UI를 켠 실제 최악 장면을 확인한다. 화면 표시를 끈 데이터 시험만으로 완료하지 않는다.
- 별도 카운터: 생성 누적, 살아 있는 적, 시뮬레이션 처리 적, 실제 화면 표시 적, 공격·투사체 수. 같은 말 '1,000마리'로 섞지 않는다.
- CPU 주 스레드/작업/렌더 스레드, GPU 프레임 시간, 메모리, 프레임당 할당, 프레임 시간 평균과 상위 지연 구간을 기록한다. 스폰·광역 처치·함정 연쇄·지형 갱신 스파이크도 포함한다.
- 목표 PC·해상도·FPS·측정 시간은 미정. 초안 후보는 목표 PC에서 1080p/60 FPS(프레임 예산 약 16.67ms)이며 사용자 확인/측정 후 정한다. 하드웨어 없이 '렉 없음'을 보장하지 않는다.
- RULES 11의 사용자 Play 절차/실제 캡처를 따른다. 최종 성능 확인에 필요한 빌드 측정은 기존 첫 마일스톤 빌드 제외 규칙의 예외가 되므로 별도 사용자 범위 승인 후 진행한다.

### 보유 에셋 우선 활용
- 사용자가 사이트 링크를 주면 종류/스타일/URP·2D 지원·자료를 먼저 검토한다. 보유 파일 경로를 받으면 실제 스프라이트·머티리얼·애니메이션·텍스처 크기·프리팹 구조를 확인한다.
- 적의 모습·배경·UI 등 기존 자원을 우선 활용하고, 대량 처리와 맞지 않는 프리팹 동작은 데이터 시뮬레이션에 연결할 표시 어댑터를 검토한다. 보유 에셋 검토 전 새 대량 그래픽 에셋을 만들거나 가져오지 않는다.
- 현재 Game/Assets는 Unity 템플릿 파일만 확인됐다. manifest에는 Entities 직접 의존성이 없고, packages-lock에는 Burst 1.8.30·Collections 2.6.8이 간접 의존성으로 확인됐다. 이 확인은 프로젝트가 Jobs/Burst 성능 구조를 이미 구현했다는 뜻이 아니다. 패키지/asmdef 변경 없음.

### C-012 r2 사용자 목표 변경 — 동시 활성 적 10,000마리
- 사용자 최신 지시: '아니다 1만마리로잡자'. 위 r1의 '우선 1,000마리 목표'를 **동시에 살아 움직이고 공격하는 적 10,000마리 목표**로 대체한다. r1은 당시 기록으로 보존한다.
- 초기 측정 단계는 1,000 → 5,000 → 10,000 동시 활성로 한다. 이동·공격·피해·함정·스프라이트 표시를 함께 켜서 확인하며, 표시만 하거나 일부 적을 정지시켜 목표 달성으로 세지 않는다.
- 10,000은 설계/검증 목표이며 현재 성능이 보장되거나 달성됐다는 뜻이 아니다. 목표 PC·해상도·FPS·에셋 실제 비용과 실측 결과로 합격선을 정한다.
- 데이터 구조·Jobs/Burst/Entities 선택·렌더링 방법은 대량 시험으로 비교 후 사용자 확정. 새 패키지 설치나 Game 구현은 이번 지시로 시작하지 않는다.
- 적 1~2종은 초기 종류 수일 뿐 총 개체 수를 줄이는 범위 제한이 아니다. 기존 첫 완주 기능 시험과 대량 적 성능 시험을 모두 유지한다.

### C-012 r3 최대 목표 — 아군 10,000 + 적 50,000 및 전투 전체 부하
- 사용자 최신 지시: '최대 우리팀 1만 적 5만까지로 잡자 목표를 최대한크게'. 아군 3,000·적 10,000 및 이전 적 10,000 목표를 **아군 10,000명 + 적 50,000마리 = 동시 활성 전투 개체 60,000** 최대 목표로 대체한다.
- 부하 범위: 병력 이동·표적·공격·피해/사망·화살/총알/포탄/마법·함정·이펙트·UI·이벤트 처리. 누적 스폰 수·화면 표시 수·비활성 풀 용량을 동시 활성 수로 바꿔 주장하지 않는다.
- 최대 목표는 성능 보장이나 달성 기록이 아니다. 목표 PC·해상도·FPS·투사체 동시 수·이펙트 예산은 미정이다.
- 단계별 예시 검증: 아군/적 1,000/5,000 → 3,000/10,000 → 10,000/50,000. 중간 단계는 측정용 예시이며 최종 목표를 낮추는 결정이 아니다.
- 화면 밖 개체의 데이터 처리와 실제 화면 안에 보이는 개체를 각각 기록한다. 실제 군중이 화면 안에 밀집했을 때의 GPU·투명 스프라이트 겹침도 따로 측정한다.
- 첫 기능 완주와 별도로 **프레임워크 기반 대량 전투 시험을 초기에 진행**한다. 최대 부하에서 수치·경로·표시·UI 전부를 실제로 검증해야 성능 완료로 기록한다.

## C-013 데이터 전투 프레임워크·풀·이벤트 경계 (제안 r1)

### 투사체 데이터 풀과 표시 풀
- 데이터 슬롯 풀: 투사체/일시 효과의 런타임 슬롯을 미리 확보·재사용. 사용 중 개수·최대치·부족 횟수·메모리량을 계측한다. 매 발사마다 관리 객체를 새로 생성/삭제하는 흐름을 기본값으로 삼지 않는다.
- 표시 풀: 화면 표현에 실제 GameObject/ParticleSystem이 필요하면 그것만 종류별로 재사용한다. '투사체 데이터 1개 = 무조건 프리팹 1개'가 되지 않게 한다.
- 핸들은 슬롯 번호 + 세대값으로 구분한다. 해제/재사용된 화살이나 적의 옛 콜백이 새로운 객체를 맞히거나 중복 반환하지 못하도록 유효성을 검사한다.
- 반환 때 수명·위치/속도·표적·소유자·관통 횟수·콜백·구독·잔상/파티클 등 종류별 상태를 정리한다. 화면 재사용 뒤 이전 효과/구독이 남지 않도록 한다.
- 풀은 무한 크기로 처음부터 예약하지 않는다. **최대 동시에 살아 있는 병력 수와 투사체 수는 별개**다. 공격률×동시 공격자×투사체 유지 시간으로 예상량을 구하고 실제 최대치와 비교해 예산을 제안한다.
- 풀이 부족할 때 핵심 투사체를 임의로 삭제해 피해를 누락하지 않는다. 제한된 확장/전투 처리 지연/발사 대기 정책은 별도 결정한다. 비핵심 화면 이펙트는 별도 표시 예산으로 줄일 수 있다.
- UnityEngine 객체 풀·UI 변경은 주 스레드 경계에서 처리한다. 작업 스레드는 스레드에 맞는 데이터/명령 큐를 사용하고 주 스레드 객체 풀을 임의로 함께 호출하지 않는다.

### 이벤트는 일괄 사건 스트림으로
- 핵심 전투 파이프라인 제안: 공격 명령 모음 → 투사체 이동/충돌 후보 → 명중 사건 모음 → 피해 일괄 적용 → 사망/함정 소비 확정 → 표시/UI 요약 사건.
- hot path의 사건은 고정 형태 값 데이터/사전 확보한 버퍼로 관리하고 타입/필드 조회를 반복 객체 리플렉션·문자열로 처리하지 않는다.
- 60,000개체가 각각 전역 EventBus에 구독하거나 개체의 매 프레임 위치를 전역 이벤트로 방송하는 구조는 기본으로 쓰지 않는다. 사건을 처리할 시스템에 좁게 전달한다.
- Jobs를 쓰면 작성/읽기 의존성과 처리 시점을 정해 버퍼를 합친다. 시스템 처리 중 재진입 콜백으로 현재 목록을 수정하거나 Unity UI를 작업 스레드에서 갱신하지 않는다.
- 게임 결과에 영향을 주는 피해·죽음·함정 소비·아이템/골드 사건은 누락/중복 금지. EventId 또는 작업/발사 핸들로 처리 중복을 막는다. 동시에 같은 적을 처치해도 사망 보상은 한 번이다.
- 버퍼 초과 때 핵심 사건을 조용히 버리지 않는다. 초과 수를 기록하고 제어된 용량/처리 정책을 적용한다. 로그 한 줄을 적/투사체마다 매 프레임 생성하지 않는다.
- UI 체력/병력 수 등의 반복 변화는 화면 단위로 합쳐 반영한다. 보고서는 의미 있는 사건을 보존하되 표시 행 수/가시 행을 관리한다. 접기/펼치기는 결과/보상을 재실행하지 않는다.
- 피해 처리 정확도와 무관한 작은 타격 이펙트는 같은 위치/시간의 사건을 시각적으로 합치거나 화면 밖 표시를 생략하는 후보를 검토한다. 실제 피해/병력 수를 합쳐 지우는 정책은 아니다.

### 대량 정확도·성능 검증
- 시나리오: 최대 병력 이동, 전원/다수 사격, 투사체 밀집, 대포/마법 광역 피해, 동시 다수 사망, 함정 연쇄, UI/보고서 폭주, 지형 편집 경로 갱신.
- 고속 투사체는 한 프레임 지점만 검사해 적을 통과하지 않도록 이동 구간 충돌 후보/판정을 검토한다. 광역 판정은 공간 후보를 먼저 좁히고 피해 정확도를 확인한다.
- 계측: 아군/적 활성 수, 보이는 개체 수, 투사체/VFX 활성/풀 보유 수, 사건 생성/처리/대기/초과 수, CPU/GPU 시간, GC 할당, 메모리, 프레임 지연과 장기 실행 증가.
- 리그레션 사례: 동시 명중에도 보상 1회, 풀 반환 1회, 재사용 핸들 안전, 프레임 이동 구간의 명중 누락 방지, UI 보고서 열기로 보상 재지급 없음, 씬 종료 시 작업/구독 정리.
- 실제 게임 구현·패키지 도입·성능 측정은 아직 수행하지 않는다. 기존 모듈 구성은 유지하고 새 인터페이스/배치/서비스 수명은 본 제안 승인 후 계약으로 정한다.

### C-012 r4 기준 장치·해상도·60 FPS 및 저사양 지원
- 사용자 요구: '60fps 2060그래픽카드' 후 '4K, CPU는 5800x정도? ram은 12g? 그냥 저가형도 쉽게'.
- 목표 GPU: RTX 2060. 정확한 모델/VRAM은 미확인. 목표 출력 해상도: **3840×2160(4K UHD 해석)**. 목표 프레임률: **60 FPS**.
- CPU/RAM은 잠정 기준: Ryzen 7 5800X급, **시스템 RAM 12GB**로 기록한다. RAM을 GPU VRAM 12GB로 해석하지 않는다. 사용자의 '정도?' 표현에 따라 최저 지원 사양 확정으로 표시하지 않는다.
- 최대 부하 아군 10,000·적 50,000 + 투사체·마법·대포·VFX·UI·이벤트 목표는 유지한다. 현재 이 사양에서 달성/무지연을 검증하지 않았다.
- 60 FPS의 프레임 간격 목표는 약 16.67ms. CPU와 GPU 단계 비용은 각각 계측하고 단순 합산해 프레임 예산으로 판단하지 않는다. 평균 FPS뿐 아니라 느린 프레임·스파이크·장기 메모리 증가를 기록한다.
- FHD 1920×1080은 약 207만 픽셀, 4K 3840×2160은 약 829만 픽셀로 4배다. CPU 데이터 처리 개선만으로 GPU 투명 스프라이트 겹침·광역 이펙트·후처리 비용이 해소됐다고 판단하지 않는다.
- **낮은 사양 지원도 별도 목표**로 둔다. 기준 PC가 모든 저가형 PC를 대표한다고 하지 않고, 지원할 낮은 CPU/GPU·FPS는 후속 측정으로 정한다.

#### 품질/성능 설정 제안 (아직 선택 미확정)
- 네이티브 4K 시험과 낮은 표시 비용의 성능 모드를 별도로 측정한다. 4K 출력에 내부 렌더링 해상도를 낮추는 방법은 사용자 질문 답변 전 채택하지 않는다. 업스케일 시험을 네이티브 4K 성능 달성으로 보고하지 않는다.
- 옵션 후보: 내부 렌더링 해상도/스케일, 화면 이펙트 수·지속시간·범위, 동적 조명/그림자·후처리, 투사체/군중 표시 품질. 도트 표현·카메라 기준은 사용자 시각 검토로 확인한다.
- 성능 모드도 실제 병력 수·피해·승패·보상·사건 정확도는 유지한다. 표시 효과를 줄인 것을 시뮬레이션 개체 제거와 혼동하지 않는다.

- 실제 기준 장치의 성능 수집은 RULES 사용자 Play 절차를 따른다. 빌드 성능 검증은 기존 범위 예외 승인 후에 한다. Game/패키지/품질 설정을 이번 문서 기록으로 변경하지 않는다.
