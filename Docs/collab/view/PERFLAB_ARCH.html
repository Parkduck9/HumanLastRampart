1. 질문: DOTS처럼 DOD로 처리해도 힘들까?

지금 시제품이 바로 DOD(데이터 중심 설계) 방식입니다. Unity DOTS는 다섯 부품의 묶음이고, 시제품은 그중 네 개를 이미 씁니다.

DOTS 부품하는 일시제품
BurstC# 계산 코드를 아주 빠른 기계어로 바꿈사용
Jobs계산을 CPU 여러 코어에 나눠 동시에 돌림사용
CollectionsJob이 안전하게 쓰는 배열(NativeArray)사용
MathematicsBurst에 맞춘 수학 타입(float3 등)사용
Entities (ECS)개체를 "엔티티 + 컴포넌트"로 관리하는 틀사용 안 함 (D-021 G2)

그럼 힘든가?

  • CPU 쪽(이동·표적·화살·피해): DOD로 하면 6만 개체도 가능성이 높습니다. 개체 하나에 하는 일이 단순하고, 같은 일을 배열 전체에 반복하기 때문입니다. 추정 합계는 약 5~8ms입니다(6장).
  • 진짜 어려운 곳은 GPU 그리기입니다. 화면에 적이 빽빽하게 몰리거나 화살·폭발 효과가 겹칠 때가 문제입니다. Entities를 써도 이 부분은 똑같습니다. 그래서 1080p로 그리고 2배로 키우는 방식(D-021 G1)을 기본으로 정했습니다.
  • Entities를 빼는 이유: Entities의 기본 그리기 기능(Entities Graphics)은 2D 스프라이트를 직접 그리지 않는 것으로 알고 있습니다. 어차피 "같은 그림 수만 개를 한 번에 그리기"는 직접 만들어야 하니, Entities의 이점이 작고 배울 것은 많습니다. (이 판단은 문서 지식 기준이며, 시제품 결과가 목표에 못 미치면 Entities와 비교합니다.)
  • 결론: DOD로 처리하는 것은 "힘든 방법"이 아니라 이 목표에 맞는 유일한 현실적 방법입니다. 남은 위험은 GPU 그리기와 설계 복잡도이고, 시제품이 그것을 숫자로 확인합니다.

6. 프레임 예산 추정과 위험 (60 FPS = 16.7ms)

모두 비슷한 DOD 구현의 일반적인 규모를 바탕으로 한 추정입니다. 5800X급 8코어를 가정했습니다. 실제 값은 순서 4 측정으로 바꿉니다.

항목 (최대 S3)추정 CPU 시간위험
적 5만 이동~0.3ms낮음
공간 격자 만들기~1ms낮음
아군 1만 표적 고르기~1~2ms중간 (밀집 칸 조회량)
화살 2~4만 이동·명중~1~2ms중간 (화살 수 예산)
사건 처리·사망~0.5ms낮음
GPU로 데이터 복사 (약 3MB/프레임)~1ms중간
CPU 합계약 5~8ms여유 있음 (추정)
GPU: 1080p 내부 렌더링빽빽한 군중 + 화살 겹침 → 측정 필요
GPU: 네이티브 4K점 4배. RTX 2060에서 가장 큰 위험 → 고품질 옵션으로만 (D-021 G1)
폭발·마법 이펙트겹치는 반투명 효과가 많으면 GPU 부담 → 표시 예산으로 조절 (피해 계산은 그대로)

7. 실제 게임으로 옮길 때

  • 시제품에서 합격한 Job·격자·화살 풀·사건 처리·그리기를 실제 전투 코드(Combat/)로 옮깁니다. 생성기·단계 전환·시험 카메라는 옮기지 않습니다.
  • 전투 시작 정보는 BattleSetup(C-005)에서 배열로 풀고, 끝나면 배열에서 BattleResult(C-006)를 만듭니다. 다른 화면은 배열을 직접 보지 않습니다.
  • 함정 판정은 같은 반경 규칙을 Core의 TrapRules(C-015)와 공유합니다. 전투 중 함정 감지는 공간 격자를 그대로 씁니다.
  • UI는 6만 개체를 직접 훑지 않고 요약 숫자만 받습니다(C-013).
